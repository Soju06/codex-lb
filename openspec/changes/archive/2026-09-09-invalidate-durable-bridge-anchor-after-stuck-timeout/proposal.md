# Invalidate the durable HTTP bridge anchor after a stuck eventless timeout

## Summary

When a fresh HTTP bridge reattach injects a durable `previous_response_id` anchor and upstream leaves that anchored `response.create` completely eventless, the request already fails closed at the existing 240-second client-safe deadline (`missing_response_created_timeout`). But the durable session row's `latest_response_id` survives that failure untouched, so the *next* reattach on the same durable session resolves the identical stale anchor and repeats the identical stall. Clear the durable anchor (and the input-fingerprint/tool-call state bound to it) when this happens, fenced to the current owner epoch, so the next reattach takes the existing unanchored path instead of replaying a reattach that has already proven dead — but **only** when the client's own incoming payload for the timed-out request already looked like a full conversation resend. A client that never resends full context has no other way to convey prior conversation state, so its anchor stays in place; see Non-Goals.

## Why

`recover-codex-desktop-idle-bridge` added the eventless `response.create` deadline specifically so a lone stuck request cannot outlive the client's own idle timeout. It intentionally fails the request closed without transparent replay or account movement. That backstop is working as designed. The gap is what happens afterward: nothing marks the durable session's stored anchor as poisoned, so a session that idle-retired and reattached with a proxy-injected anchor rebuilds the identical anchored `response.create` on the next turn and stalls again, indefinitely, until the client abandons its local continuation state and starts a fresh session.

Production evidence in [#1534](https://github.com/Soju06/codex-lb/issues/1534) confirms this exact loop: a session with ~425 stored items, no `custom_tool_call`/interleaved-developer shape (so [#1527](https://github.com/Soju06/codex-lb/pull/1527)/[#1537](https://github.com/Soju06/codex-lb/pull/1537)'s prefix-scanner fix does not cover it), idle-retires after a long tool call, reattaches with `fresh_reattach_anchor_injected`, stalls for 240s, and repeats on every subsequent turn. The owner confirmed on the issue that this post-timeout behavior is a defect and that invalidating the durable anchor for that `bridge_key` so the retry takes the fresh no-anchor path is "a bounded, fail-closed recovery consistent with the existing fresh-session path" ("Track 2"); the reporter confirmed this is exactly the fix that matches what they observed. This is also the same underlying mechanism the broader investigation in [#1167](https://github.com/Soju06/codex-lb/issues/1167) isolated to a 2-request repro: a bridge session created fresh for a request that already carries a `previous_response_id` (proxy-injected or client-supplied) can go silent forever.

## What Changes

- Add a fenced durable-bridge-repository write that clears `latest_response_id`, `latest_input_item_count`, `latest_input_full_fingerprint`, and `latest_pending_tool_calls_json` for a session, scoped to the current `owner_instance_id`/`owner_epoch` (a no-op if a newer owner already holds the row). `latest_turn_state` and the session's identity/aliases are left untouched, because the eventless anchor is what's implicated, not the session itself.
- Track, on the request state, whether the client's own incoming payload already looked like a full conversation resend at the moment codex-lb injected the anchor (`request_state.proxy_injected_anchor_had_full_resend_payload`), independent of whether that resend passed the stricter same-request in-place-replay safety proof (`fresh_upstream_request_is_retry_safe`).
- When the HTTP bridge upstream reader retires a session for `missing_response_created_timeout`, and at least one of the requests that hit the eventless deadline both carries a proxy-injected `previous_response_id` **and** had a full-resend-shaped payload, clear that durable session's anchor before releasing durable ownership. A proxy-injected anchor on a genuine delta-only payload is left in place: the client has no other way to convey prior context, so clearing it would replace a visible, bounded timeout with a request that upstream could silently accept as a new, context-free conversation.
- Leave a client-supplied `previous_response_id` untouched: this change only clears an anchor codex-lb itself injected, matching the existing scope boundary that client-supplied anchors are the client's own responsibility (see `preserve-fresh-bridge-full-resends`, `recover-codex-ws-stale-anchor-with-canonical-code`).
- Emit a structured, low-cardinality bridge event when the anchor is invalidated, alongside the existing `missing_response_created_timeout` / stuck-retire telemetry.
- Add unit coverage for the new fenced repository write (including the stale-epoch no-op) and HTTP-bridge regressions proving: a full-resend-shaped proxy-injected anchor is cleared; a delta-only proxy-injected anchor is left intact; a client-supplied anchor is left intact.

## Capabilities

### New Capabilities
- None.

### Modified Capabilities
- `responses-api-compat`: A durable HTTP bridge session's proxy-injected anchor is invalidated after its `response.create` proves eventless at the client-safe deadline, but only when the client's own payload for that request already looked like a full conversation resend, so the next reattach on that session takes the existing unanchored path instead of repeating the same anchor injection.

## Non-Goals

- No change to the 240-second client-safe eventless deadline itself, or to its terminal failure behavior for the request that times out (`recover-codex-desktop-idle-bridge`); this change only affects what happens to the durable row afterward.
- No change to client-supplied `previous_response_id` handling, prefix-scanner classification (`preserve-fresh-bridge-full-resends`, [#1537](https://github.com/Soju06/codex-lb/pull/1537)), or cross-account/owner-unavailable recovery.
- No change to account selection, routing, or account-health penalties; this is a same-account, same-session durable-state cleanup.
- **Delta-only proxy-injected anchors are explicitly out of scope and remain on today's behavior** (repeated 240s stalls until the client abandons its local continuation state). A genuine delta-only client — one whose incoming payload never looks like a full resend because it relies entirely on codex-lb's transparent `previous_response_id` bookkeeping — has no other way to convey prior conversation state once the anchor is gone. For that shape, clearing the anchor would let upstream accept the bare follow-up as a new, context-free conversation: a 200 response with a reply that has no memory of anything before it, and no error to signal that. Today's 240s stall is visible and bounded; this would not be. See `design.md`'s Load-bearing assumption; extending coverage to this shape is an explicit follow-up pending maintainer input, not an oversight.
- Does not overlap with the open [#1394](https://github.com/Soju06/codex-lb/pull/1394) recovery/retry-circuit work: that PR's `recover-fresh-hard-bridge-timeouts` and `recover-safe-http-bridge-continuations` changes explicitly keep previous-response/proxy-injected-anchor requests pinned and fail-closed when no proof-gated full-resend body exists, which is exactly the case this change addresses for the *next* distinct request. This change touches the same `durable_bridge_repository.py` / `durable_bridge_coordinator.py` / `http_bridge/upstream_events.py` files, so it may need a rebase once #1394 lands, but the two are functionally independent.
