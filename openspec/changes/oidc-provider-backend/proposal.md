## Why

Phase 2 built the whole shape of company sign-in and then stopped one step short of it. `dashboard_auth_providers` already has a row kind called `oidc`, an encrypted `config_encrypted` column whose docstring says it holds OIDC secrets, an `AuthProviderKind.OIDC` enum member, `AuditAuthMethod.OIDC`, and an `_PASSWORDLESS_KINDS` set that already lists `oidc` so that enabling it will demand a qualifying break-glass account. The `AuthProvider` protocol's docstring reserves `begin_login`/`complete_login` "when they arrive". `IdentityResolver` already refuses an unknown identity by default and already writes the `login_failed reason=unknown_identity` row with the subject, e-mail and groups. What does not exist is the one thing that turns all of that on: a provider that talks to Okta, Entra ID, Google Workspace, Keycloak or Authentik directly, instead of requiring the operator to put oauth2-proxy in front of the load balancer.

The registry says so in a comment — `a kind without an implementation (oidc before Phase 3) is never active`. This change is the line that makes that comment false, and nothing else. PLAN.md §4.6 and the Phase 3a row specify it: Authorization Code with PKCE, a discovery document, `state` and `nonce`, the client secret encrypted at rest with the existing `TokenEncryptor`, configuration in the dashboard and nowhere else (D6), claims mapping through the same `IdentityResolver` every other provider uses, and a pre-flight test login before the provider may be turned on — the lesson Immich and Langfuse published after their operators locked themselves out.

## What Changes

- **`OidcProvider`**, the second implementation of the `AuthProvider` protocol after `TrustedHeader`. Authorization Code + PKCE (S256 only), discovery document, `state` and `nonce`, and ID-token validation against the JWKS the discovery document advertises. It defines `resolve_identity` returning `None` (it recognises nobody from a bare request) plus the `begin_login`/`complete_login` pair the protocol docstring reserved, and it ends in `get_identity_resolution_cache().resolve(...)` like everything else — no provider-specific branch in any route, no forked JIT, no forked re-evaluation.
- **Configuration in the dashboard, in one encrypted blob.** Issuer, discovery URL, client id, client secret, redirect URI and the four configurable claim names (subject, email, name, groups) are sealed as one JSON document into the existing `dashboard_auth_providers.config_encrypted` with `TokenEncryptor`. `PATCH /api/auth-providers/{id}` gains a typed `config` object, accepted only on an `oidc` row; `GET` returns every field except the secret in clear and the secret as `****` plus its last four characters.
- **Writing that document is delegation-bounded by everything.** An identity provider asserts *who someone is*, so repointing it reaches every account — further than any role the endpoint's role fields can hand out. Writing `config`, turning `linkByEmail` on, and enabling a row that already hands out a role the caller could not delegate all require the caller to hold every grant the admin preset holds (`403 insufficient_delegation`); the narrowing directions stay open. **No environment variable, no `Settings` field, no `.env.example` line, no tier entry** — D6, and `Settings` is at 96/96 against its ratchet anyway.
- **Four endpoints under the existing `/api/dashboard-auth` prefix**, so no router and no `include_router` line is added: `GET /oidc/login/start` (public, 303 to the IdP), `GET /oidc/callback` (public, 303 back into the app), `POST /oidc/test-login/start` (`security:write`) and `POST /oidc/step-up/start` (the signed-in account). Both browser-facing routes are `GET`, so **the CSRF exemption list is not touched**: a `response_mode=form_post` callback would be a cross-site `POST` that `DashboardCsrfMiddleware` rejects before routing, and the tempting fix is an exemption that weakens every route behind it.
- **Flow state that is single-use across replicas and bound to one browser.** A new `dashboard_oidc_login_flows` table keyed on the SHA-256 of the `state` holds the hashed `nonce`, the PKCE verifier encrypted with the same `TokenEncryptor`, the purpose, the acting account and the redirect URI; a short-lived sealed cookie holds the `state` itself. The callback needs both, and consumes the row with one conditional `DELETE … RETURNING` **before** it exchanges the code, so a replayed code, a reused `state` and two racing replicas all end the same way.
- **Claims to identity.** `sub` becomes the subject **verbatim** — case-sensitive by specification, unlike the trusted-header path that case-folds — bounded by the same 512-character column width; e-mail, name and groups come through the configured claim names; groups are case-folded so the existing `match_role_id` rules match them. An e-mail the IdP explicitly marks unverified is dropped rather than carried, because `link_by_email` and `email_domain` rules would otherwise act on a self-asserted address.
- **Just-in-time provisioning defaults to deny**, by seeding the `oidc/default` row disabled with `unknown_identity_role_id` NULL. The refusal, the `/auth/pending` landing and the `login_failed reason=unknown_identity` audit row naming provider, identity, e-mail and groups are the resolver's existing behaviour, reached by handing it an identity — not re-implemented here.
- **The test-login proof.** Two columns on `dashboard_auth_providers` (`test_login_user_id`, `test_login_verified_at`). A successful test login by an admin stamps them and audits `oidc_test_login_succeeded`; enabling the row requires a stamp by *that same account* within the last ten minutes and otherwise answers `409 oidc_test_login_required`, checked inside the account write intent `update_provider` already takes and beside the break-glass gate it already runs. Writing the connection configuration clears the proof, and a successful enable consumes it. The stamp names a *configuration*, not just a moment: the flow row carries a digest of the document it was started against and the stamping write is conditional on the row still holding it, so a configuration `PATCH` that lands mid-round-trip cannot be handed a proof for an issuer nobody tested.
- **SSO session TTL and `prompt=login` as a step-up factor.** An OIDC session is capped at the existing `REMOTE_DASHBOARD_SESSION_TTL_SECONDS` (12 h) through the `max_ttl_seconds` lever `_create_user_session` already has — no new constant, no new setting. `step_up_methods()` returns `["oidc"]` for an account that holds neither a password hash nor a TOTP secret and has an identity on an active OIDC provider, which is exactly the account that answers `403 step_up_unavailable` today; an account that holds a local factor is unchanged, because letting a live IdP session substitute for a password the account has would be a downgrade, not a feature. For the same reason `/totp/verify`'s automatic step-up is narrowed to a session that a *local password* minted: an OIDC session is fresh and carries `password_verified` — the flag the session gate reads — without any password having been presented. The re-authentication is forced (`prompt=login`, `max_age=0`) and *verified* through `auth_time` rather than assumed.
- **Audit.** Only `oidc_test_login_succeeded` is new. `provider_enabled`/`provider_disabled` already fire from `update_provider`; `login_failed reason=unknown_identity` already fires from the resolver; `login_success`, `step_up_verified`, `user_created` and `identity_linked` already exist. A flow that fails validation audits `login_failed` with `reason: oidc_login_failed` and a coarse `stage`, and never carries a code, a `state`, a `nonce`, an ID token or the client secret — `_sanitize_details` would not have caught any of them.
- **One new dependency: `pyjwt[crypto]`.** It brings only `cryptography`, already a direct dependency. The alternative is hand-writing RS256/ES256 verification, JWKS-to-key conversion and algorithm selection over `cryptography` primitives — the code an adversarial reviewer of an authentication flow goes looking for first, and where `alg: none`, RS256-as-HMAC confusion and attacker-chosen algorithms live. The library owns the crypto; this change owns the egress, so `PyJWKClient` (which does its own blocking `urllib` fetch with no timeout, no size bound and no SSRF check) is **not** used.

Not in this change: the three-step connect wizard, the "continue with `<IdP>`" button and the pending screen's reference code (PR-3a-2); SCIM and back-channel logout (Phase 3b); audit webhooks (Phase 5a); custom roles (Phase 5b); a `userinfo` fallback for IdPs that publish groups only there; and the `invite_sso_email_unverified` rule of §4.6, which belongs to the resolver's invite step and is not reached by any path this change adds.

## Capabilities

### Modified Capabilities

- `identity-providers`: the OIDC provider and its encrypted dashboard configuration, discovery and JWKS caching with key rotation, ID-token validation, claims-to-identity mapping, and the test-login proof that gates enabling the row.
- `admin-auth`: the four sign-in endpoints, the single-use browser-bound flow state, the twelve-hour SSO session that is not a local password session, and identity-provider re-authentication as a step-up factor for an account that has no other one.
