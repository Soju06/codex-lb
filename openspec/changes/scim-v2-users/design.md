## Context

Three properties of what is already on main shape every decision below.

**The deprovisioning half is built and has no caller.** `DashboardUsersService.deactivate_user(user_id, *, actor: AuditActor, actor_ip, source)` takes the accounts write intent *before* its first read (so SQLite stays on `BEGIN IMMEDIATE` instead of the row-less fallback), reads, returns `False` without writing or auditing when the account is already inactive, runs the qualifying break-glass post-state predicate, re-applies the same count as an `EXISTS` predicate inside its conditional `UPDATE`, cascades the owned keys with `deactivated_reason='owner_disabled'`, bumps `session_generation` (which is the whole of "sessions revoked" — the cookie carries `sg`), invalidates both caches, and audits. On a break-glass refusal it emits `scim_deprovision_refused` at WARNING **itself** and re-raises. Nothing in `app/` calls it.

**There is no principal-free way back.** Reactivation is two principal-bound halves: `update_user(principal, …, {status: "active"})`, which runs `assert_can_act_on`, `assert_can_delegate` and the invite/credential rules and deliberately restores no keys, and `reactivate_keys(principal, …)`, whose `UPDATE` reads the owner's status in an `EXISTS` predicate and therefore must run *after* the status flip has committed. A machine caller cannot use either without inventing a `DashboardPrincipal`, and inventing one would hand a bearer token a blanket `assert_can_act_on` bypass on every account in the install. That is the single most likely way this change could introduce a privilege escalation, so it is the first thing ruled out.

**`IdentityResolver.resolve()` does not fit, and its rules do.** `resolve()` requires a `DashboardAuthProvider` row; `AuthProviderKind` is closed at `password | trusted_header | oidc` and the registry refuses any kind it has no implementation for, so a `scim` provider row could never be active and SCIM is not a sign-in method anyway. `_provision()` hard-codes `role_source=mapping` and derives the role from role mappings and `unknown_identity_role_id`, while SCIM's role comes from the pushed slug. What *is* reusable, and what "reuse the resolver rather than fork its rules" means here, is the part that is pure: `slugify_subject`, `jit_username_candidates`, the `_free_username` walk that reserves `admin`, the `_identity_row` shape, the three-attempt `IntegrityError` retry, and the "e-mail already taken stays on the identity row" rule. The provisioning half is parameterised with `(role_id, role_source)` and given a narrow entry point, so one copy of the slug rules survives. SCIM never goes through `IdentityResolutionCache`: that is a five-second login-path throttle that opens its own session, and a provisioning write must not be answered from it.

## Goals / Non-Goals

**Goals**

- An identity provider creates joiners and disables leavers without an administrator in the loop, and the disable is the same event, with the same cascade and the same refusals, as the one an administrator would have caused by hand.
- A bearer token that can do exactly that and provably nothing else.
- Every refusal an identity provider can provoke arrives as a SCIM error an identity provider's log will render, naming what to change.
- An install whose identity provider is compromised, or whose SCIM token leaks, does not thereby gain an administrator.

**Non-Goals**

- `/scim/v2/Groups`, the mapping re-evaluation a group push drives, and `/scim/v2/ServiceProviderConfig` (3b-2). Back-channel logout (3b-2). Audit webhooks (5a).
- SCIM as a sign-in method. No `scim` `AuthProviderKind`, no provider row, no seeded row, nothing in `_active_providers()`.
- A second SCIM namespace on one install. The column that would carry it exists and is enforced; no interface varies it.
- Reconciling a SCIM-provisioned account with the same person's OIDC sign-in. That has an existing, gated answer and this change surfaces it rather than inventing a second one — see *Convergence*.

## Decisions

### An identity provider push may not create an admin, and may not promote to one

This is the decision the rest of the security posture hangs on, so it is derived rather than asserted.

`assert_can_delegate(caller, target)` requires every `(permission, scope)` of the role being handed out to be at or below the caller's own; its docstring states the consequence, that only an admin preset holder can grant the admin preset. Every path in this codebase that names a role passes through it — `create_user`, `update_user`, the role-mapping writes, the provider role fields. A SCIM bearer token is not a `DashboardPrincipal` and holds no grants at all, so on the letter of that rule it can delegate nothing. An unbounded `roles` slug would make the SCIM push the only role-assignment path in the product that never meets the gate, which is a delegation hole by construction rather than by oversight.

§4.6's A1 analysis settled the analogous question for provider configuration and is the closer precedent: the levers that let a machine assert *who somebody is* — writing an OIDC `config`, turning on `link_by_email`, arming a row that already holds a role — are gated on `assert_can_delegate(principal.grants, ADMIN_GRANTS)`, the strictest check in the plan, because whoever controls them can point the install at their own identity provider and mint a token carrying an existing administrator's subject. A SCIM token is the same class of lever: it asserts identities *and* names roles, with no human in the loop per push. It must be bounded at least as tightly, not less.

Two things follow, and they are separate gates rather than one.

**Issuing or rotating a SCIM token is an `ADMIN_GRANTS` delegation.** The route sits under `security:write` and inherits the step-up requirement that covers every non-safe `security:write` request, and on top of that it runs `assert_can_delegate(principal.grants, ADMIN_GRANTS)` and answers `403 insufficient_delegation` otherwise. Revoking is never gated — the narrowing direction stays open everywhere in this plan.

**A pushed `roles` slug is still bounded below admin level, and the bound is in code, not on the token row.** The tempting alternative — record the issuer's grants on the token row as a delegation ceiling and let an admin-issued token push `admin` — was rejected for three reasons. First, §4.2's fifth qualifying fact exists precisely to exclude the account a SCIM push would create: a provisioned admin has no `password_hash`, so it can never open the local sign-in form, and it therefore counts toward `last_admin_protected` while contributing nothing to the qualifying break-glass count. Let an identity provider mint those at scale and an install reaches a state with many active admin-preset accounts and zero qualifying ones — "the tightening succeeded, the identity provider then failed, nobody can sign in locally" — which is the exact degenerate state the fifth fact was added to make unreachable. Second, a ceiling snapshot outlives its issuer: demote or delete the administrator who issued the token and an admin-minting machine credential is still in the install with no principal left to reason about, which is the "row nobody wrote" footgun §4.6 identified for `enabled: true`. Third, this codebase already ships one IdP-shaped path that quietly mints admins — the seeded `trusted_header/default` row defaults `unknown_identity_role_id` to the admin preset under D10 — and adding a second is the wrong direction of travel.

So: a pushed slug is accepted only when `resolve_assignable_role` accepts it *and* `is_admin_level(resolve_role_grants(role))` is false. Today that is `operator` and `viewer`; `ASSIGNABLE_PRESET_ROLES` already excludes `guest` and `member`, and Phase 3's picker is presets-only, so no custom role is reachable here either. An `admin` push is a provisioning error with its own reason, distinct from a typo, and **never a silent downgrade to viewer** — the Sentry lesson cuts both ways, and an operator who is told "admin is not provisionable, assign it by hand" can act, while one whose admins silently became viewers cannot. Promotion stays a human action through `PATCH /api/dashboard-users/{id}`, where `assert_can_delegate` has a real principal; that route already refuses a role change on an account whose `role_source` is not `manual` unless `force: true` is sent, and its text is already generic over `role_source`, so `scim` needs no change there.

`member` deserves its own message. It is a seeded, real, recommended-by-the-plan slug that `resolve_assignable_role` refuses until Phase 4, so an identity provider administrator who follows the documentation gets a refusal that reads like a bug. Its detail says so in as many words.

**One predicate, every direction.** `_provisionable(role)` — assignable *and* not admin-level — is the whole of what this surface may hand out, and it therefore bounds every lever that could put somebody on the far side of it. Three of them, and the first two were originally missing:

1. *The role it writes.* Already derived above.
2. *The role it removes.* A pushed slug moves the role only when `role_source` is `scim` **and** the account's current role is one this predicate accepts. A role a bearer token may not grant is one it may not take away either — not out of symmetry for its own sake, but because `deactivate_user` decides whether the last-admin invariant applies by reading the role the write is about to leave behind (`_is_admin_preset(user)` over `role_id`). Let one request demote an admin-preset account to `viewer` and disable it, and the guard reads `viewer`, finds no admin to protect, and disables the install's last administrator. Refusing the demotion closes that without touching the shared function.
3. *The account it switches on.* `active: true` is the only direction of this surface that *grants* access — it restores the account and every key the disable cascaded — and it was the one direction that re-checked nothing: deprovision re-checks break-glass and last-admin, a role push re-checks assignability and `role_source`, and an enable re-checked neither. `PATCH {"active": true}` on an account an administrator had promoted by hand and then disabled answered `200`, put it back on the admin preset and revived its keys, while the very same response reported `"roles": []` — the surface knew the role was one it may not hand out and switched the account on anyway. The enable now passes `_provisionable` over the role the request leaves the account holding, read before the commit that expires it, and answers `409` otherwise. An `active: true` for an account that is already active is not an enable and is not refused, so a directory re-pushing an administrator's resource on a schedule does not collect a permanent error.

### One parser, two verbs

A `PATCH` used to be a second reading of the same wire format, and every way in which the second reading was weaker than the first was a defect: it took the first entry of a multi-entry `roles` array where a `PUT` answered `400`, it ignored `primary` on `emails` so the identical payload stored a different address, it applied no `max_length` at all — invisible on SQLite, a `500` from a `varchar(128)` column on PostgreSQL — and it refused `title` and `locale` with `400 invalidPath`, taking the `active: false` batched beside them down with it. Keeping two parsers aligned by comment was never going to hold.

So a patch is not parsed. It is *folded* — each operation's `path`, or each key of a no-path operation's value object, writing one entry of an attribute dictionary, with `emails` and `roles` widened from the three shapes identity providers send (a bare string, one object, a list) into the one the resource schema declares — and the result is then handed to `ScimUserRequest.model_validate`, the model a `PUT` body is validated by. Everything the two verbs must agree about lives in that model and in the one `_changes()` that reads it: the caps, the cardinality bounds, `primary`, `_display_name`'s `displayName`-beats-`name.formatted` precedence, the at-most-one `roles` rule, and the `externalId` immutability check. The only input the two verbs differ on is *which attributes the request named* — a `PUT` names all of them, a `PATCH` names what it carries — and that set is the sole argument that distinguishes them.

Two fold rules fall out and are deliberate. An attribute the resource does not model is **ignored**, exactly as a `PUT` body ignores it: `extra="ignore"` on the model does the ignoring for both verbs, so the promise made in *Rate limiting and a bounded body* is now structurally true rather than true of one verb. And an attribute named **twice** in one request is refused, because the fold has to discard one of the two writes and the discarded one could be the value that should have been refused — two operations setting `roles` to `admin` and then to `viewer` used to leave `admin` unexamined, so it produced neither the mandated refusal nor its audit row.

### The token is a digest in a unique index, confirmed in constant time, rotated in place

Generation follows the API-key path: a single random string of 256 bits (`secrets.token_urlsafe(32)`) behind a short non-secret marker, `token_hash = sha256(plain).hexdigest()` in a `UNIQUE` column, and `token_prefix` — the leading characters of the marker plus a few of the body — stored in clear so the card can say which token is which.

Verification hashes the presented value and looks the row up by equality on that unique index. That is the house pattern and it is the correct one: the comparison is against a digest inside an index, a wrong guess produces an uncorrelated digest, and there is no byte-prefix oracle to leak — demanding a constant-time compare over the table would force a linear scan of every row, which is strictly worse. Because this change will be reviewed adversarially on exactly this point, the fetched row is then confirmed with `hmac.compare_digest(row.token_hash, presented_hash)` before it is trusted. That second compare is redundant and cheap, and it makes the property hold under any future lookup that stops being an index equality.

The token never reaches a log. It rides in a header, so it is not in a request line, a query string or a redirect; `log_error_response` records only category, request id, method, path, status, code and message. The audit sanitiser is not a safety net here — it *drops* keys by exact name from a fixed set, and `scim_token_id`, `token_prefix` and `token_label` are not in it — so the rule is simply that no detail dictionary ever carries the secret or its digest under any name. Only the row id and the label ever appear.

Rotation is in place on the same row: a new plaintext, `token_hash` and `token_prefix` replaced, `rotated_at` stamped. The row id, the label and the last-sync history survive, and the previous secret stops working the instant the write commits, because the row is the only verifier. Revocation is a row delete; the identity rows the token wrote are keyed by `provider_key`, not by the token, so revoking and re-issuing resumes against the same accounts rather than orphaning them.

**One-shot display.** The plaintext appears in the `201` of issue and the `200` of rotate and in nothing else — no list, no read, no later response, no audit row. The card follows the invite dialog rather than the OIDC one, because the OIDC card's secret flows the other way (write-only, masked on read) and has no one-shot problem to solve. The rules the invite dialog established and this card copies: the value lives in parent-owned React state and never in a query cache, in storage, in a URL or in mutation variables; the dialog is owned *outside* the subtree the issue itself re-renders; and the list refetch and session refresh are deferred until the person dismisses it. That last one is not hygiene, it is correctness here: issuing the first token flips `access_summary.scim_tokens` to 1, which flips the disclosure tier to `enterprise`, which re-renders the Organisation group — and a dialog mounted inside the card would unmount mid-copy, taking the only copy of the secret with it.

### A SCIM token is not a principal, and the shape of the code is what proves it

`validate_scim_token` returns a frozen `ScimTokenData(id, label, provider_key)` and never writes `request.state.dashboard_principal`. No `DashboardPrincipal` is constructed anywhere on this path — there is deliberately no empty-grant constructor, and adding one would make a machine token indistinguishable from a session at every `principal.has(...)` call site. This is the `app/modules/fleet/api.py` shape exactly: a bearer surface returns its own typed row and reads every scoping decision off that row's own columns.

The negative half is what gets tested. The `/api/` route-permission matrix test is scoped to the dashboard prefix and would never see these routes, so this change adds the mirror assertion: every route on the SCIM router carries the SCIM bearer dependency, and no route's dependency tree contains `DashboardPermissionDependency` or `validate_dashboard_session`. That single test is the only mechanical proof that a SCIM token grants no dashboard permission; without it a future route added to this router with no dependency ships silently. Three more properties ride with it: the SCIM surface never sets a cookie, a dashboard session cookie never authenticates it (there is no cookie fallback), and an `sk-clb-…` API key presented as a SCIM bearer is refused, because the two live in different tables with different digests and the SCIM path consults only its own.

The step-up gate must not reach here either. "Sensitive mutations require a recent step-up" binds every non-safe `security:write` request; a SCIM push has no account to re-verify, so the routes stay outside that gate by having no permission dependency at all, and a test pins it rather than leaving it to a broad principal check that might one day be widened.

**Tenancy.** There is no tenant or organisation concept anywhere in this codebase, so "no confusion between tokens" reduces to a scoping field that is real and enforced rather than decorative. `dashboard_identities.provider_key` is that field — it is already the discriminator in `UNIQUE(provider, provider_key, subject)` — and the rule is that the value comes from the **token row**, never from the request body, a header or a path segment, and is applied to every lookup, every insert and every resource resolution the token makes. A SCIM `id` that names an account without a `scim` identity under this token's `provider_key` answers `404`, not `200`. Every token this change issues carries `default`, as the trusted-header and OIDC rows do; the column is enforced anyway, because the alternative — deriving the namespace from the request — is the bug the requirement exists to prevent, and a scoping field that exists and is unenforced is worse than none.

That scoping is also the principal-free equivalent of `assert_can_act_on`: a SCIM token can only ever address accounts bound to a `scim` identity in its own namespace. The install's local administrator, the break-glass account, and every account provisioned by another path are simply not addressable, so the SCIM surface cannot enumerate them either — which matters, because listing them would be the `users:manage` read this token is denied.

### The error envelope is RFC 7644's, with no invented members

Every response body from `/scim/v2`, including every refusal, is `application/scim+json`. Refusals are

```
{"schemas": ["urn:ietf:params:scim:api:messages:2.0:Error"], "status": "<code as a string>", "scimType": "<keyword>", "detail": "<sentence>"}
```

with `scimType` present only where RFC 7644 §3.12 defines a keyword for the case, and no product-specific member added. The dashboard's own error shape is *not* reused: `mapped_user_errors()` emits the dashboard envelope, and `_error_format(request)` returns `None` for a path outside `/api/` and `/v1`, so without explicit handling the four forgettable cases — `RequestValidationError`, the `404`/`405` on an unmatched path, an unhandled exception, and the `413` the ingress middleware raises before routing — would answer in FastAPI's or the dashboard's shape instead. The router registers its own handlers for all of them.

| Condition | Status | `scimType` | Detail says |
|---|---|---|---|
| Missing, malformed, unknown, rotated-away or revoked bearer | `401` | — | Authentication failed. One sentence for all five, plus `WWW-Authenticate: Bearer`; the cases are never distinguished |
| `userName` absent or empty on create | `400` | `invalidValue` | which attribute is required |
| Unknown role slug | `400` | `invalidValue` | the slug, verbatim as pushed |
| Recognised slug that is not assignable (`guest`, `member`) | `400` | `invalidValue` | the slug, and that this release does not provision it |
| Recognised, assignable, admin-level slug | `400` | `invalidValue` | the slug, and that an administrator assigns it by hand |
| More than one `roles` value, by either verb | `400` | `invalidValue` | that one role is carried |
| Unparseable body, unknown `op`, one attribute named twice in one `PATCH` | `400` | `invalidSyntax` | what was not understood |
| A patched value over a modelled attribute's length or cardinality cap | `400` | `invalidSyntax` | the same sentence the identical value on a `PUT` earns |
| A `PATCH` operation with no `path` whose value is not an object of attributes | `400` | `invalidPath` | that such an operation carries an object |
| `externalId` changed after create | `400` | `mutability` | that `externalId` is immutable |
| `active: true` on an account whose role this surface does not provision | `409` | — | the account, and that an administrator enables it by hand |
| Any filter that is not `userName eq` | `400` | `invalidFilter` | the supported filter |
| Create whose `externalId` is already provisioned here | `409` | `uniqueness` | the existing resource id, so the caller can `GET` it |
| Deprovision leaving zero qualifying break-glass accounts | `409` | — | the break-glass sentence, naming the account |
| Deprovision leaving zero active admin-preset accounts | `409` | — | that another administrator must remain |
| Unknown id, or an id outside this token's namespace | `404` | — | nothing about which of the two it was |
| `DELETE /scim/v2/Users/{id}` | `405` | — | `PATCH {"active": false}`, plus an `Allow` header |
| Any other unmatched `/scim/v2/…` path | `404` | — | — |
| Body over the route bound | `413` | — | the bound |
| Rate limited | `429` | — | plus `Retry-After` |

`uniqueness` and `mutability` are RFC keywords used where the RFC uses them; the `409`s that are this product's invariants carry no `scimType`, because §3.12 requires one only for `400` and inventing a keyword would be off-spec for the sake of a machine reader that does not exist. The administrator-facing reason lives in the audit row, which is where an administrator looks.

Two envelope cases are easy to miss and are specified deliberately: `DELETE` is a spec-visible behaviour of this change and goes straight through the `405` path, and unmatched `/scim/v2/…` paths only reach a handler at all once `scim/` joins the SPA fallback's excluded prefixes — until then `GET /scim/v2/Groups` answers `index.html` with `200`, which an identity provider reads as "groups are supported".

### A `userName` collision derives a new name; it never takes an account over

Accounts are never resolved by username — only by the `(provider, provider_key, subject)` identity triple, or by an invite that expects exactly that triple. That is the module's rule and it is what makes this safe: a pushed `userName` is an *input to naming*, never a claim about which account is meant.

So a create resolves its account by `externalId` alone. The local `username` is then derived: `slugify_subject(userName)` case-folds, maps `@` to `.`, drops everything outside `[a-z0-9._-]` and cuts to 56 characters; `_free_username` walks `stem`, `stem-2`, `stem-3`, … skipping any name that is taken and always skipping the reserved `admin`; the insert retries three times on `IntegrityError`, re-checking each time whether the identity triple landed concurrently. An identity provider pushing `alice@example.com` onto an install that already has a local `alice.example.com` gets a new account named `alice.example.com-2`, and the existing account is not read, not written and not linked. A push for `admin` gets `admin-2` and cannot inherit the migrated break-glass row. The install's e-mail uniqueness is honoured the same way the resolver honours it: an address another account already holds stays on the identity row and the new account's `email` is left null. That check is re-read on each retry rather than only before the first attempt — `dashboard_users.email` is unique, so a writer that claims the address between the check and the commit turns the insert into an `IntegrityError` the identity triple cannot explain, and a retry carrying the same address forward would spend every remaining attempt on the same violation and answer a routine joiner push with a `500`.

The local username is assigned **once**. A later `userName` on replace or patch updates what the identity provider calls the person and does not rename the account, because renaming from a machine push would put the slug rules in a fight with `username_taken` and would let one push move another account's name out from under it.

That leaves `userName eq` needing something to match, and the account's own username is the wrong thing: our charset has no `@`, so `alice@example.com` can never equal a local username and the identity provider's own reconciliation query would miss every account it created. `dashboard_identities` therefore grows one nullable `user_name` column, written only by this path, carrying the value as pushed; it is the resource's `userName` and the filter matches it case-insensitively. The schema requirement for that table names the unique triple and the cascade rather than enumerating columns, so this is additive. The alternative — matching the slug of the filter value against local usernames — cannot express the collision family (`alice.example.com` and `alice.example.com-2` are different people) and would have made rediscovery ambiguous exactly where it matters.

Rediscovery after deprovisioning falls out of this: `deactivate_user` does not touch `dashboard_identities`, so the row, its `user_name` and its `externalId` all survive, and `userName eq` finds the disabled account. That is also why `DELETE` is not implemented and why the account row is kept even in the `invited` case.

### Convergence with the company sign-in is the existing gated lever, surfaced honestly

A SCIM identity is `provider='scim'`; an OIDC sign-in writes `provider='oidc'`. They are different rows by design — §4.2 models one person as N identities across N providers — and nothing in this change makes one imply the other. The consequence has to be said out loud: on an install where SCIM provisions joiners and OIDC signs them in, the first sign-in of a provisioned person resolves no `oidc` identity, finds no invite, and — with `link_by_email` off, which is the default — provisions a *second* account.

This change does not invent a fix. The mechanism already exists, is deliberate, and is gated: `link_by_email` on the OIDC provider row, whose widening direction requires `assert_can_delegate(principal.grants, ADMIN_GRANTS)` precisely because it decides who somebody is. Inventing a SCIM-side e-mail link would be the same lever with no gate and no human consent, which is exactly what §4.6-A1 forbids. For accounts that predate SCIM there is a second existing path: an invite that expects an identity triple, which the resolver's step 1.5 links instead of provisioning, and which a SCIM create honours the same way.

What this change owes is honesty rather than magic: when a company sign-in provider is enabled and `link_by_email` is off, the card carries one advisory line naming what will happen, with the control that turns it on. That converts an invisible data-integrity problem into a visible one, costs a line of copy and a predicate, and leaves the decision with the human the delegation rule says owns it.

### The card is disabled before a company sign-in provider is enabled, and says why

The gate is "a provider row whose `kind` is not `password` and whose `enabled` is true", read through a predicate in `features/organisation/rules.ts` with its own unit test rather than inline in the card, because §4.8's third rule forbids scattering predicates across components. It reads the **provider rows the group already holds**, not `access_summary.providers_enabled` as first drafted: the summary is absent for a caller holding `security:write` without `users:manage`, and that caller is exactly the person this group is for — deriving the gate from the summary would tell them nothing is connected on an install where something is. The rows are already fetched, already gated on the same permission, and already the source the sibling cards read.

Disabled means the issue control is disabled and the card states the reason in the plan's own words — connect company sign-in first — not that the card is hidden: a hidden card teaches nobody that automatic account management exists, and this group's collapsed line already promises it. The address stays readable while disabled, because an operator preparing the connection at the other end needs it before anything here is switched on.

**The collapsed line grows one sentence, for the install this gate cannot describe.** A credential outlives the provider it was issued against: switch the company sign-in back off and the install has `scim_tokens = 1`, no non-password provider and, possibly, an unrestricted password sign-in. Counting tokens in `isOrganisationConfigured` — which §4.8 requires, or the first credential flips the disclosure tier while the collapsed line still says nothing is set up — makes that install *configured*, and the existing ladder would then have fallen through to the login-policy sentence and claimed a restriction that is not there. So the ladder gains "accounts are added and removed automatically", with and without the restriction clause. Neither sentence contains a banned word.

The reason is real rather than procedural. A SCIM-provisioned account has `password_hash` null and no identity any local form can accept; until a company sign-in provider is enabled, every account this surface creates is an account nobody can use. Issuing a token first would produce an install full of unusable accounts and an administrator with no signal about why.

The rest of the card is the group's ordinary shape: a `<section>` with the icon header, an `AlertMessage` slot under it, the base URL as a copyable `font-mono select-all` fact next to the token list, and issue / rotate / revoke through the group's shared mutations bag with its `settle()` that invalidates and refreshes the session — except that the issue and rotate mutations defer that refresh until the secret dialog is dismissed, for the reason given above. The card takes `{query, mutations, disabled}` from the body and calls no permission hook of its own; the group owns the `security:write` gate. It mounts last, after the login-policy card, which is position (d) in §4.8's order.

`access_summary.scim_tokens` becomes the real row count. Without it the first token flips nothing: the collapsed line keeps reading the unconfigured one-liner and the enterprise tier never fires, so the card becomes undiscoverable the moment the group collapses. `isOrganisationConfigured` learns about tokens for the same reason. The collapsed line's wording is unchanged and still contains none of the banned words — the card's own name, "automatic account management", is already in the sentence the group has shipped since 2c-2.

### Ordering, atomicity and the things that must not be called

The deprovisioning request is two phases and the order is load-bearing.

`DatabaseRateLimiter.check_and_increment` and `record_failure` both `commit()`, and a commit releases the accounts write intent. §4.2's F5/F6 rule is that the count and the write sit in one uncommitted transaction with the intent taken before the first read. So the rate-limit budget is spent **first, on its own**, and only then does the request enter the deactivation transaction. Getting this backwards silently breaks the break-glass guard's atomicity, which is the kind of defect that never shows up in a test that does not race.

Inside the transaction: `acquire_write_intent()` → read → guard → cascade keys → delete the invite, if the account still had one → the conditional `UPDATE` carrying both `EXISTS` predicates → `commit_user(bump_generation=True)`. The invite DELETE is not conditional on the invite still being live: an account leaving `invited` has no use for a spent one either, and the lazy purge only ever looks at `invited` accounts, so a row left behind would be unreachable from then on. `_purge_expired()` is never called from this path: it commits when it purges and **rolls back when it does not**, which would throw away the whole pending transaction. `deactivate_user` already avoids it for this reason and the SCIM service must too.

Two corrections to `deactivate_user` ride along because the SCIM envelope makes them visible. When its conditional `UPDATE` matches zero rows it raises `LastAdminProtectedError` unconditionally, even when the break-glass predicate was the loser — `update_user` and `delete_user` both re-read the counts to pick the right error, and without the same branch a racing SCIM deprovision returns the wrong `409` detail. And it returns `False` for `status='invited'`, so an identity provider deprovisioning a hand-invited joiner does nothing at all and the invite — which never expires when it is `sso_only` — stays live. The invited case now deletes the invite and moves the row to `disabled`, auditing `invite_revoked` alongside `user_disabled` so one search still answers when an invitation stopped working; the row is kept, unlike a human revoke which deletes the account, because `userName eq` has to keep finding it. Both corrections force one more change of their own: the username and role id are read off the row *before* the conditional write, because the rollback on the refusal path expires every attribute and reading one back afterwards is synchronous IO on an async session — it would surface the refusal as a driver error rather than as a `409`.

Reactivation is the mirror and its ordering is equally load-bearing: the status flip must **commit** before `reactivate_owner_disabled_keys` runs, because that `UPDATE`'s `EXISTS` predicate reads the owner's status. That is also why reactivation is a separate action in the dashboard rather than a side effect of the status PATCH. Only rows with `deactivated_reason='owner_disabled'` come back; `manual` and `expired` are untouched, and the other side of that rule is already enforced — `ApiKeysRepository.update` re-stamps `manual` on an explicit revoke and refuses `isActive: true` while the owner is disabled.

**`apply()` is three phases, and each exists because merging it into another produced a defect.** The whole update path shares one `AsyncSession` — `get_scim_context` composes the SCIM repository, the users repository and `DashboardUsersService` over it precisely so this can be true — and the phases are:

1. *Refuse first.* Every guard a push can fail is evaluated before a single attribute is assigned: `resolve_pushed_role`, and the enable bound above. Both read the account row, and both must read it before the commit that expires every attribute on it — reading one back afterwards is synchronous IO on an async session, which surfaces as a driver error rather than as the `409` it was supposed to be. The values the later phases still need (`username`, `subject`, the pushed slug) are captured here for the same reason, exactly as `deactivate_user` already captures its own.
2. *Write only what changes.* Each attribute is compared before it is assigned, and the identity's `last_seen_at` is stamped only if something really moved. Without that, a redelivered `active: false` still wrote a row and committed — undoing, from the outside, the idempotency `deactivate_user` and `reactivate_user` promise by returning `False` without writing. "A replayed push costs the account nothing" now includes the surface that calls them.
3. *Commit once.* The attribute writes stay **pending** across the lifecycle call, so `deactivate_user`'s own `commit_user(bump_generation=True)` carries them and its refusal path — the explicit rollback, or the raise that leaves the transaction to the session teardown — takes them back. Committing them first, as the original did, meant a push carrying a rename and an `active: false` refused by the break-glass invariant answered `409` while the rename had already landed. When the lifecycle is a no-op, or when the request changes no status at all, the caller commits the pending writes itself; when there is nothing at all to write it rolls back instead, so a no-op push does not hold SQLite's single writer slot while the response is built.

### Rate limiting and a bounded body

Two buckets, mirroring the deliberate two-bucket shape the password login already documents: a coarse per-address ceiling and a narrow per-token bucket. The narrow bucket is keyed on the **token row id** and never on the token or its digest — `rate_limit_attempts.key` is plaintext in the database and the digest is the verifier, so keying on it would store a credential-equivalent. An unauthenticated request spends only the address bucket, because there is no row to key on yet.

The body bound is at the route, not the ingress. `request_body_limit_for_path` returns 32 MiB for anything outside the proxy paths, which is not a bound for a SCIM endpoint in any useful sense, and adding a third global budget would mean verbatim-copying two `http-ingress-limits` requirements of six and five scenarios each for one number — the exact shape of copy that has already dropped assertions twice in this campaign. Instead: `max_length` on every string attribute, a hard cap on the number of `Operations` and on multi-valued attributes, and a declared `Content-Length` check on the route that answers the SCIM `413` before the body is read — followed by a check of the received length, because a declared length is the caller's claim and not a fact. Attributes the resource does not model are **ignored, not refused**: every identity provider sends more than a core user (`meta`, `title`, `locale`, phone numbers, an enterprise extension), so refusing them would turn a routine Okta or Entra push into a `400` while protecting nothing the byte bound does not already protect. The bound is the body size and the caps, not the attribute vocabulary. The list `count` is clamped to a maximum rather than refused, which is what RFC 7644 allows a server to do; `startIndex` is one-based as the RFC requires.

### Audit events

`scim_user_provisioned` and `scim_user_deprovisioned` are the plan's own names. `scim_deprovision_refused` already exists and is emitted **inside** `deactivate_user`, so the route maps the exception to a `409` and does not audit again — a duplicate row per refusal is precisely what an adversarial review looks for. Three names the plan does not enumerate are added and justified here rather than silently:

- `scim_provision_refused` (WARNING, details `reason` ∈ {`unknown_role`, `role_not_assignable`, `role_not_provisionable`, `account_not_provisionable`}, the slug or the account's role, the external id and the token row id), because scope requires an audit row for a refused slug and none of the existing names means it. The fourth reason is the refused **enable** — the same refusal ("this surface does not hand that role out") reached from the other direction, so it takes the same event rather than a fourth name, and it carries the role in the audit row even though the response body deliberately does not.
- `scim_role_push_ignored` (WARNING, details `reason` ∈ {`role_source_manual`, `role_not_provisionable`}, the pushed slug and the account), because the requirement that a skipped role push be "audited once rather than on every push" has no existing name and no existing row. *Once* needs a marker, and the row is its own: the surface reads `audit_logs` for `(action, target)` before writing, which is why this one event is `await AuditService.log(...)` rather than the fire-and-forget `log_async` used everywhere else — the next push has to be able to see it. It is written after the request's own transaction has ended, so the separate session the sink opens is never queued behind the writer slot this request holds, and a request refused for any other reason writes no row at all, because the push it belonged to did not happen. `idx_audit_logs_target` covers the read.
- `scim_token_issued` / `scim_token_rotated` / `scim_token_revoked` on the dashboard side, because every other enterprise object type in this group audits its writes and a credential that can disable accounts is not the one to make an exception for.

The actor on a push is constructed directly — `AuditActor(user_id=None, username=None, role_slug=None, auth_method=AuditAuthMethod.SCIM.value)`, the shape the resolver already uses — because `AuditActor.from_principal` needs a principal and there is none. Reactivation adds no new event: the shared functions already audit `user_enabled` and `user_keys_reactivated`.

## Risks / Trade-offs

- **A duplicate account on first sign-in** when `link_by_email` is off. Accepted, surfaced on the card, and not fixed here: the fix is a lever the delegation rules say a human must pull.
- **`member` refused with a message that reads like a bug.** Mitigated by naming it in the detail and in the spec; it resolves itself in Phase 4.
- **One nullable column on a table this change does not own.** Justified by `userName eq` being unable to work otherwise, additive against the requirement that governs that table, and written by exactly one path.
- **The resolver's demotion path still does not cascade owned keys.** Pre-existing, now written down instead of implied, and deliberately left for a change whose one concern it is.
- **No `ServiceProviderConfig`.** Some identity providers probe it. Deferred with Groups rather than shipped as a document that would have to lie about group support for one change.
