- [x] 2.3 `app/modules/scim/dependencies.py`: `ScimTokenData(id, label, provider_key)` frozen, `validate_scim_token(request, credentials)` over its own `HTTPBearer(auto_error=False)` — its own rather than the core one, whose description names the proxy API key and whose surface must stay separable. - [x] 2.4 The dashboard side: `GET`/`POST`/`POST {id}/rotate`/`DELETE {id}` under the existing dashboard router's `security:write`, inheriting the step-up gate, with `assert_can_delegate(principal.grants, ADMIN_GRANTS)` on issue and rotate and nothing extra on revoke. ## 3. The SCIM surface

- [x] 3.1 `app/modules/scim/schemas.py`: the user resource, the `ListResponse`, the `PATCH` operation model (case-insensitive `op`, `active` coerced from a boolean and from `"true"`/`"false"` in any casing), and the error envelope. Every string attribute carries a `max_length`; `Operations` and multi-valued attributes are capped; attributes the resource does not model are ignored rather than refused, because every identity provider sends some and the bound is the body size, not the vocabulary.
- [x] 3.2 `app/modules/scim/api.py`: the router, `POST`/`GET {id}`/`PUT {id}`/`PATCH {id}`/`GET`, the `405` for `DELETE` with its `Allow` header, the declared-`Content-Length` check answering the SCIM `413` before the body is read, `application/scim+json` on every response, and a `set_scim_error_format` marker plus a `scim` branch in each shared handler — `RequestValidationError`, `StarletteHTTPException` (the `404`/`405`), the unhandled-exception catch-all and the pre-routing ingress `413` — following the `set_dashboard_error_format` precedent rather than registering a second set of handlers, with a `/scim` path fallback in `_error_format` for the unmatched paths a router marker never reaches. The status/`scimType` table is `design.md`'s.
- [x] 3.3 `app/main.py`: include the router with the others (before the SPA fallback), and add `scim/` to the fallback's `excluded_prefixes` so an unmatched `/scim/v2/...` is a SCIM `404` rather than `index.html` with `200`.
- [x] 3.4 `app/modules/scim/service.py`: resolution by `(scim, token.provider_key, externalId)` or an invite expecting exactly that triple; provisioning through the resolver's shared helpers with an explicit `(role_id, role_source=scim)`; `userName` stored on the identity row and never used to resolve an account; the e-mail-already-taken rule, re-read on each retry so an address claimed after the check is dropped rather than repeated; the duplicate-`externalId` `409 uniqueness` and the changed-`externalId` `400 mutability`; `userName eq` matching the stored value case-insensitively and including disabled and invited accounts; `count` clamped, `startIndex` one-based.
- [x] 3.5 The role gate: trim and case-fold, `get_role_by_slug`, `resolve_assignable_role`, then `is_admin_level(resolve_role_grants(role))` must be false. Three distinguishable refusal reasons — `unknown_role`, `role_not_assignable` (`guest`, `member`), `role_not_provisionable` (admin-level) — each a `400` naming the slug verbatim plus one `scim_provision_refused` row. Absent `roles` on create provisions `viewer`; no refused value ever reaches that default. A pushed slug moves the role only on create, or when `role_source` is `scim` **and** the current role is one `_provisionable` accepts — a role this surface may not grant is one it may not take away, because `deactivate_user` reads the role the write leaves behind to decide whether the last-admin invariant applies. A skipped push audits `scim_role_push_ignored` once per account, gated on reading that row back.
- [x] 3.6 One parser for two verbs: `changes_from_patch` folds the operations into a user-resource attribute dictionary (widening the bare-string and single-object spellings of `emails`/`roles`), validates it through `ScimUserRequest` — the model that reads a `PUT` body — and hands the result to the one `_changes()` both verbs call. Unmodelled attributes are ignored by `extra="ignore"` for both; an attribute named twice in one request is `400 invalidSyntax`; the only thing the verbs differ on is which attributes the request named.
- [x] 3.7 `apply()` in three phases: refuse before any write (the pushed role, and the enable bound `_provisionable` over the role the request leaves behind, both read before the commit that expires the row); assign only values that actually change, stamping `last_seen_at` only beside one; and leave the attribute writes pending so the lifecycle function's own commit carries them and its refusal rolls them back. `_set_active` returns whether it wrote, so the caller knows whether to commit or to release the write intent.

## 4. Lifecycle wiring

- [x] 4.1 `active: false` → `deactivate_user(user_id, actor=AuditActor(user_id=None, username=None, role_slug=None, auth_method=AuditAuthMethod.SCIM.value), actor_ip=…, source="scim")`, mapped to the SCIM envelope. The route does **not** audit `scim_deprovision_refused`; the function already does. `_purge_expired()` is never called from this path.
- [x] 4.2 `deactivate_user` learns two things: the `invited` case (delete the invite in the same transaction, move the row to `disabled`, keep the row, audit `invite_revoked`), and re-reading the counts when the conditional write matches no row so the refusal names the invariant that actually lost instead of always reporting the last-admin one. New repository primitive `delete_invite(user_id)` — invite gone, account row kept, which nothing existing does. It is not conditional on the invite still being live: an account leaving `invited` has no use for a spent one either, and the lazy purge only looks at `invited` accounts, so a row left behind would never be reached again. The row's `username` and `role_id` are read before the write, because the rollback on the refusal path expires every attribute and reading one back then is synchronous IO on an async session.
- [x] 4.3 `reactivate_user(user_id, *, actor, actor_ip, source)`: the principal-free twin. Write intent before the first read, status to `active`, **commit**, then `reactivate_owner_disabled_keys` — that order is load-bearing because the restoring `UPDATE` reads the owner's status in an `EXISTS` predicate. Audits `user_enabled` and `user_keys_reactivated` through the shared paths; no new event name. It stays general: the bound on *who* a push may enable is the SCIM surface's own predicate and lives with the surface that owns it, not in the shared back-channel function.
- [x] 4.4 `app/modules/dashboard_auth/service.py`: `scim_tokens` counted for real in `access_summary` instead of the hard-coded `0`.
