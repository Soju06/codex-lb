# Change: bound-conversation-raw-tail-index-range

## Why

The two most expensive statements in production `pg_stat_statements` are the dashboard's distinct-conversation reads (`conversation_count` / `conversation_request_count` from `GET /api/dashboard/overview`, ~3 s mean, and the hour-multiple conversation trend buckets, ~1.5 s mean). Both are built on `conversation_presence_union`, whose raw `request_logs` branch LEFT OUTER JOINs the single `account_usage_rollup_state` row and filters with `watermark IS NULL OR requested_at < lo OR requested_at >= least(watermark, hi)`. Because that OR references a joined column and carries an `IS NULL` disjunct, PostgreSQL can only apply it as a post-scan filter: the only index condition is the outer `requested_at >= since [AND < until]`, so every poll walks the whole 7-day window (14 days per overview poll, the previous-period call scanning 7 cold days to return a handful of rows) although the fold lag bounds the true un-folded tail to about 2-3 hours. Every other rollup reader in the same module already emits constant raw windows and is absent from the slow-statement list.

## What Changes

- `app/modules/accounts/usage_time_rollup_read.py`: `conversation_presence_union` reads the conversation watermark as an uncorrelated scalar subquery of the state row inside the same statement instead of joining the state row into the UNION branches. The raw complement of a window `[since, until)` with folded hours `[lo, hi)` is the two constant half-open ranges `[since, lo)` and `[greatest(lo, least(coalesce(W, lo), hi)), until)` — the sub-hour leading edge and the un-folded tail — emitted as `requested_at < lo OR requested_at >= tail_start`, which PostgreSQL plans as a BitmapOr of two `requested_at` index ranges (the scalar subquery becomes an InitPlan parameter inside the Index Cond; SQLite plans a scalar subquery plus an index search). The folded branch bounds `bucket_epoch` by the same watermark through a scalar subquery. A missing state row (`NULL`) coalesces to `lo` and an epoch watermark clamps to `lo`, so both degrade to exactly the legacy raw read as before.
- `conversation_labeled_presence_union` is removed. Its only callers were the reports summary and per-day conversation counts, which `report-aggregation` moved onto the permanent report aggregates (`app/modules/reports/rollup_read.py`, own `reports_folded_through` watermark); the helper has been uncalled since, and this change deletes it rather than rewriting dead code. The reports path is not touched.
- The single-snapshot contract is unchanged: each dashboard conversation read is still ONE statement, with the folded segment, its raw complement and the watermark coming from the same snapshot. No caller signature changes (`request_logs` repository untouched), no schema change.
- No new `CODEX_LB_*` setting and no kill switch, deliberately: the change only rephrases a predicate whose result set is provably identical for every watermark position (the complement of the folded hour buckets, pinned row-for-row by the new tests and by the existing parity harness), so there is no behaviour an operator could want to opt out of; the existing degradation path (epoch or missing watermark → exactly the legacy raw statement) already covers the "rollup is wrong, read raw" escape hatch through the documented state-row reset, and a second toggle would only add a configuration surface with nothing to select.
- Tests: a focused module pins (1) union aggregates against a raw-only oracle for every watermark position relative to the window — state row missing, epoch, before, inside, after — over aligned, unaligned and open-ended windows with and without display buckets and soft-deleted rows; (2) that the two switched dashboard statements read the watermark as scalar subqueries (no `JOIN account_usage_rollup_state`, no `conversation_folded_through IS NULL`); (3) on PostgreSQL, `EXPLAIN (ANALYZE)` of the bind-parameter statement the application sends shows every `request_logs` node as an index/bitmap scan with an Index Cond on `requested_at`, zero rows removed by filter, and exactly the oracle's raw-complement row count — for the watermark missing, below the window, equal to the window's first folded hour (the `greatest` clamp), inside, equal to the window end (the `least` boundary), a half-hour past the window end, and a fully folded hour-aligned window (zero rows). The module is appended to `POSTGRES_PYTEST_TARGETS`.

Out of scope (separate concerns, follow-ups): replacing `COUNT(DISTINCT)` over the union with a `GROUP BY` form (decide after measuring the folded satellite's 7-day cardinality on production), memoizing the weekly trailing-demand deltas, and live-row partial indexes for the facet skip scan.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `query-caching`: MODIFIED requirement "Distinct-conversation reads combine the presence rollup with a raw live tail in one statement" — the snapshot sentence gains the mechanism ("the watermark read from the state row inside the same statement as an uncorrelated scalar subquery in each branch, never joined into the branches as a column") and a new sentence requires the raw complement to be expressed as bounds on `requested_at` so it is served by bounded index ranges, never by a per-row filter over a joined watermark column; two scenarios added (index-bounded raw complement; results independent of the watermark position relative to the window). The requirement title, the reports paragraph (permanent report history source per `report-aggregation`), the degradation sentence and the existing five scenarios are kept verbatim.

## Impact

- Code: `app/modules/accounts/usage_time_rollup_read.py` only (the conversation-presence block and the module docstring; `conversation_labeled_presence_union` deleted). The caller in `app/modules/request_logs/repository.py` is unchanged; `app/modules/reports/` is not touched.
- Tests: `tests/integration/test_conversation_presence_union.py` (new), `Makefile` `POSTGRES_PYTEST_TARGETS` (+1 file). The parity harness `tests/integration/test_request_usage_rollup_parity.py` stays the regression oracle and is unchanged.
- Operators: no action; no configuration, schema or API change. Dashboard overview and conversation trend reads stop scanning the full window on PostgreSQL.
