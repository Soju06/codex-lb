## Why

Release N moved every dashboard credential into `dashboard_users` and then kept writing a copy of the compat `admin` account's password hash, TOTP secret and replay counter into the `dashboard_settings` columns it had just stopped reading, so a replica still running the previous release would keep seeing the truth. That scaffolding cost three things: the projection itself (eight write paths, an optimistic-version retry loop that exists only so two rows commit together, and a two-row replay guard), the `409 compat_user_locked` refusals that stood in for the mirror wherever a mirror was impossible (the compat account could not be disabled, deleted or renamed, and the install-wide TOTP requirement could not be turned on while that account had not enrolled), and the pin that kept the bootstrap account named `admin` — because the mirror is gated on the *name*, a rename in release N would have silently stopped it.

That is one mechanism, not three, which is why they come out together. PLAN.md's Phase 5 line queues exactly this work for the release after Phase 1: "레거시 컬럼 이중기록 제거·삭제, 부트스트랩 사용자명 변경 허용, `compat_user_locked` 제거". Phases 0, 1 and 2 are merged; the reprojection revision `20260909_020000_reproject_compat_admin_credentials` has already copied the legacy values onto the account row, so the columns carry nothing the users table does not. Leaving them one release longer is not free either: with the mirror gone they stop being a projection and become an unowned copy of a live password hash and an encrypted TOTP secret that `DELETE /api/dashboard-auth/password` no longer clears and no code path ever rotates. The mirror is what kept them honest; removing the mirror is what makes dropping them necessary.

## What Changes

- **The dual write is deleted.** `DashboardAuthRepository` stops mirroring on all seven paths (`create_first_admin`, `set_user_password_hash`, `rotate_user_password`, `set_user_totp_secret`, `try_advance_user_totp_step`, `clear_user_credentials`, and the `mirror_legacy` seam in `_write_user`) and `codex-lb admin reset-password` stops mirroring on the eighth. `dashboard_users` becomes the sole authority with no second writer. The replay guard keeps its first `UPDATE … WHERE totp_last_verified_step IS NULL OR totp_last_verified_step < :matched` verbatim, keeps rolling back and returning `False` when it changes zero rows, and loses only the second statement — so a replayed code is still refused, and `disable_totp`'s commit boundary (the code is spent before the break-glass guard, PLAN F5) is unchanged.
- **The non-mirror writes buried in the mirror closures are re-homed, not deleted.** Three of the columns those closures touched are still authoritative and are *not* being dropped: clearing the dashboard password also clears `totp_required_on_login`, `totp_required_for_admin_role` and the bootstrap token; setting or changing a password clears the bootstrap token; self-service TOTP disable turns `totp_required_on_login` off. Deleting the closures wholesale would leave a passwordless install with `requires_auth` true and no account able to sign in — the state the `dashboard_auth_migration_inconsistency` warning was added to detect — and would stop `/password/setup` and `/password/change` from invalidating a live remote bootstrap token. Each write moves onto its own settings path and stops being conditional on the account's name. Two of them change behaviour for the better: password removal now resets both requirements on any single-account install rather than only one named `admin` (the account can now be renamed, so the name-keyed version was already a latent bug), and self-service TOTP disable resets the install-wide requirement only when the acting account is the install's **only account** — counting disabled accounts and live invitations, not only active ones — whereas today a compat `admin` in a team could turn an install-wide security setting off from a self-service route that carries no `security:write`.
- **`compat_user_locked` goes, all four raise sites.** Three are `CompatUserLockedError` in `DashboardUsersService` (role/status PATCH, DELETE, `reset-totp` while `totp_required_on_login` is on); the fourth is `CompatAdminUnenrolledError` in `SettingsService`, which refuses the off→on transition of `totp_required_on_login` through `PUT /api/settings` and is translated to the same wire code from a different module. The migrated account becomes an ordinary account: it can be demoted, disabled, deleted and reset like any other, subject to the rules that apply to everyone (`self_modification_forbidden`, `last_admin_protected`, `credential_required`, `insufficient_delegation`, and the break-glass post-state guard). `TotpEnrollmentSummary.compat_admin_unenrolled` leaves the `/api/settings` response. **This is a user-visible unblock on a security setting, not a no-op**: every migrated install that still has an unenrolled `admin` can finally require two-factor at sign-in.
- **The bootstrap account can be renamed** — as an admin action on an existing account, **not** as a field on the bootstrap screen. `PATCH /api/dashboard-users/{id}` accepts `username?`, validated by the same normalization and reservation as account creation, answering `409 username_taken` on collision, under `users:manage` + step-up + `assert_can_act_on`, audited as `user_renamed`. `POST /api/dashboard-auth/password/setup` still takes `{password, bootstrap_token}` and still creates the account as `admin`; the bootstrap screen gains no field and a one-account install sees no new control at all (§4.11 tier (a) hides the username field and the People tab; PLAN §4.11 rule ② bans the word from personal copy). The reservation of the name `admin` stays — for account creation, invite acceptance, the rename itself and the reverse-proxy JIT slug — so the rename is one-way and the name in `docs/sso.md`'s runbooks can never belong to someone else.
- **First-run setup re-arms by row, not by name.** `create_first_admin` looks the existing row up by `COMPAT_ADMIN_USERNAME` today while inserting the deterministic compat id. Renaming the account to `alice`, removing the password (which keeps the row) and posting setup again would miss the lookup, collide on the id, and answer `409 password_already_configured` forever — a renamed install that could never be re-bootstrapped. The predicate moves onto the row (the credential-less break-glass account carrying the compat id), which is what `The username admin is reserved` already says normatively.
- **`CompatAdminProjection` is deleted as the dead code it already is.** Nothing in `app/` or `tests/` has ever constructed it; only `COMPAT_ADMIN_USER_ID` is imported out of that module. Its docstring claims to be the funnel every legacy write passes through, so anyone mapping this change from that file alone would miss all eight real call sites. The constant moves next to `COMPAT_ADMIN_USERNAME` in `app/db/models.py`, `app/modules/dashboard_users/compat.py` goes, and `tests/unit/test_dashboard_users_compat.py` — the only guard keeping the two migrations' frozen literals equal to the runtime constants — points at the new home. The migrations keep their frozen literals and import nothing from `app.*`.
- **The migration drops three columns**: `dashboard_settings.password_hash`, `dashboard_settings.totp_secret_encrypted` and `dashboard_settings.totp_last_verified_step` — exactly the three the projection wrote, and the three nothing in `app/`, `scripts/`, `config/` or `crates/` reads. The guest columns, both bootstrap-token columns, both TOTP requirement flags and `local_login_policy` all stay. One revision on the current single head `20260912_000000_merge_thread_cache_and_bridge_retirement_heads`, inspector-guarded in both directions, `op.batch_alter_table` for SQLite. The downgrade re-adds the three nullable columns **and re-projects them from the row carrying the frozen compat id** — not from the username, which after this release is no longer a stable way to find the bootstrap account.
- **Upgrade order is a contract, and the code enforces the part it can.** See below.

Not in this change: H8 (the `/internal/drain/*` loopback check reading `request.client.host` instead of the raw peer — separate issue) and H9 (the `__Host-` cookie prefix, optional). Nothing about OIDC, SCIM, API key policies or custom roles.

## The rolling-deploy constraint

This release is **not rolling-upgrade safe. Old replicas must be stopped before the migration runs.** Concretely, and in both directions:

- A **previous-release (pre-N)** replica reads the legacy columns as its authoritative credential. Its 1a-2 reprojection has not run, so it has no other source. After the drop it does not merely go stale — its settings reads name a column that no longer exists and fail.
- A **release-N** replica is no better off. It maps all three columns on `DashboardSettings` and loads the row as a full ORM entity (`session.get(DashboardSettings, 1)`, plus the `select(DashboardSettings)` in the upstream-proxy resolver and the CLI), so every settings read emits their names. And it still *mirrors*: a password change or a TOTP enrolment on the compat account issues `UPDATE dashboard_settings SET password_hash = …` against a dropped column. Both fail.
- The chart makes the window unavoidable under a stock upgrade: the Helm migration Job is a `pre-upgrade` hook at weight `-5` running `python -m app.db.migrate upgrade`, so the DDL commits **before** the new pods roll and therefore before the old pods drain.

So the instruction is: **drain old first** — blue/green with the old colour stopped (or `replicaCount` taken to zero, or `migration.enabled=false` with the Job run by hand after the stop) before the migration runs. That is the same posture release N already required for the version-2 cookie rename, which is the closest thing this campaign has to a precedent; the difference is that release N got a free fence (the cookie rename made old code fail closed, so everybody signed in once and noticed), and this release has no such fence. Nothing forces an operator off the old colour, which is why the release note is an instruction and not a footnote, and why the guard below exists.

**Rollback is supported to release N only.** The downgrade re-creates the columns and re-projects them from the compat-id row, which release N ignores (it reads `dashboard_users`) and release N-1 reads as the credential. If the bootstrap account was deleted — now possible — there is nothing to project and a pre-N build would read the empty columns as "never bootstrapped": an implicit local admin and a fresh bootstrap token. That is stated in the release note as an unsupported rollback target, not left to be discovered.

**The guard.** `run_upgrade()` — the one choke point shared by the CLI, the Helm Job, the container entrypoint and `run_startup_migrations()` — checks the stamped revision **before any DDL**, using the side-effect-free inspection that is already there, and when the drop is about to run on a non-empty database it emits a single `WARNING` naming the drain requirement. An operator who never opened the release notes is told once, by the process that is about to do it.

**The guard refuses nothing, deliberately.** Skipping release N is safe: the drop descends from `20260909_020000_reproject_compat_admin_credentials`, so one `upgrade head` from any older revision re-projects the credentials onto the account rows and only then drops the columns they came from. A refusal keyed on "this ledger never applied release N" would have demanded a two-step upgrade that applies exactly the same revisions in the same order — no data safety bought — while `run_startup_migrations()` is the boot path, so it would have stopped every install of an earlier release from starting. The ordering that makes the jump safe is a property of the revision graph and is asserted by a test.

**What the guard cannot do**, stated here so nobody reads more into it: it cannot see a live old replica. There is no version heartbeat anywhere — `scheduler_leader` holds a leader id and `bridge_ring_members.metadata_json` holds an endpoint URL. The co-existence window is covered by the documented upgrade order, by that one warning, and by the fact that an old replica fails loudly rather than quietly — by nothing else.

## Capabilities

### Modified Capabilities

- `dashboard-users`: the projection requirement is removed; the source-of-truth requirement loses the write-only mirror and keeps a single-row replay guard; the compat refusals leave the edit, delete and account-action requirements; the edit requirement gains `username?`; the drop revision and the re-homed install-wide settings writes are new.
- `admin-auth`: first-run setup stops naming the legacy columns and re-arms by row; the `admin` reservation is restated as a name reservation with an id-keyed re-arm; the TOTP-requirement gate loses its `409 compat_user_locked`; the "legacy columns are not consulted" scenario becomes "they no longer exist".
- `frontend-architecture`: the People tab stops hiding controls on the migrated row and gains Rename; the login form's anti-flap rule stops keying on the literal `admin`.
- `database-migrations`: the pre-upgrade ledger guard and its warning.
- `user-documentation`: the upgrade order, the rollback limit and the corrections to the four paragraphs that promise the old behaviour.
