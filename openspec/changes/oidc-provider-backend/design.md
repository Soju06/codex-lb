## Context

Phase 2 left an OIDC-shaped hole and marked its edges: `AuthProviderKind.OIDC`, `config_encrypted`, `AuditAuthMethod.OIDC`, `_PASSWORDLESS_KINDS`, the `begin_login`/`complete_login` note in the protocol docstring, and the registry comment that names `oidc` as the kind with no implementation. Everything downstream of the provider — JIT with its default deny, the four-step lookup order, the re-evaluation table, the slug rules, the last-admin pin, the per-identity throttle, the `login_failed reason=unknown_identity` row — is written, tested and on main. This change writes the provider and the four endpoints around it, and touches nothing downstream.

Two facts shape almost every decision below. First, the deployment is multi-replica behind HAProxy, so the callback routinely lands on a replica that did not run the start; anything the flow needs must be in the database or in the browser, never in process memory. Second, the operator supplies the issuer URL, which makes this the first feature in the product where a dashboard setting causes the server to make an outbound request to a host of the operator's choosing and then trust what comes back.

## Goals / Non-Goals

**Goals**
- A company connects Okta, Entra ID, Google Workspace, Keycloak or Authentik from the dashboard, with no environment variable and no file on the host.
- Every security property an adversarial reviewer of an authentication flow checks is decided here explicitly and is checkable in one requirement each, rather than being an emergent property of the code.
- The provider is a thin adapter: it produces an `ExternalIdentity` and stops. No route branches on the provider kind, no JIT rule is duplicated, no audit event the resolver already writes is written twice.
- Turning it on cannot lock the install out: the break-glass gate that already exists plus a proof that the operator's own browser completed a round trip through this exact configuration, within ten minutes, from this exact account.

**Non-Goals**
- The three-step connect wizard, the "continue with `<IdP>`" button and the pending screen's reference code (PR-3a-2). This change makes the wire facts the wizard needs true; it renders nothing.
- SCIM, back-channel logout (3b), audit webhooks (5a), custom roles (5b).
- A `userinfo` fallback. All claims come from the ID token, which is one signed artifact. An IdP that publishes groups only at `userinfo` (large-group Entra tenants) is served by configuring a claim the IdP does put in the ID token; adding a second, separately-fetched claim source is a follow-up with its own caching and failure questions.
- Multiple simultaneous OIDC providers. `provider_key` stays `default`, matching the single-instance convention `password` and `trusted_header` use. Nothing in the schema forbids a second row later.
- The `invite_sso_email_unverified` rule of PLAN §4.6. It belongs to the resolver's invite step, is not in the resolver's canonical requirement today, and is not reached by any path this change adds. Recording it here as unfinished is more honest than half-implementing it in a provider.

## Decisions

### The ID token is verified by `pyjwt[crypto]`, and the JWKS fetch is not

There is no JOSE library in the project: `jwt`, `jose`, `authlib`, `joserfc`, `jwcrypto` and `oauthlib` are all absent from `pyproject.toml`, from `uv.lock` and from the virtualenv, and nothing transitive supplies them. The only existing token reader, `extract_id_token_claims` in `app/core/auth/__init__.py`, base64-decodes the payload **without verifying the signature** — correct for a ChatGPT token the process just fetched over TLS from a hard-coded host, and a critical vulnerability if reused for an IdP token that arrives through a browser.

So one of two things must happen, and both cost something. Hand-writing verification over `cryptography` means writing base64url-JSON decoding, JWKS-to-public-key conversion for RSA and EC, `kid` selection, and algorithm selection — about 150 lines holding the four classic failures (accepting `alg: none`, honouring an attacker-supplied `alg`, verifying an RS256 token as HS256 so the public key becomes the HMAC secret, and verifying over the wrong serialisation). Adding `pyjwt[crypto]` costs a `pyproject.toml` and `uv.lock` change and a supply-chain entry — but its only new transitive dependency is `cryptography`, which is already a direct dependency of this project.

We add the library. The rule that makes it safe is not "the library is careful" but how it is called: the candidate key is selected from the JWKS by `kid` first, the permitted algorithm list is derived from **that key's own type** intersected with the IdP's advertised `id_token_signing_alg_values_supported` and with our own allow-list of `RS256/RS384/RS512/PS256/PS384/PS512/ES256/ES384/ES512`, and the token header's `alg` is never an input to that choice. Passing an RSA public key with `algorithms=["RS256"]` is precisely the shape PyJWT refuses to run as HMAC. `iss`, `aud` and expiry are validated by `jwt.decode` with `options={"require": [...]}` so a missing claim is a refusal rather than a `None`.

`jwt.PyJWKClient` is deliberately **not** used. It performs its own blocking `urllib` fetch, on the event loop, with no timeout, no response-size bound, no redirect policy and no host validation — every property this change has to own. The JWKS bytes are fetched by us and handed to `jwt.algorithms.RSAAlgorithm.from_jwk` / `ECAlgorithm.from_jwk` as data.

### JWKS caching, and what happens when the IdP rotates a key

One process-level cache, keyed by `(provider_id, digest of the connection document)`, holding the discovery document and the parsed key set together — they are fetched together and they expire together, and keying on the document means **any configuration write drops the entry on that replica with no invalidation message at all**, while other replicas drop theirs the moment they read the changed row through the 5 s provider registry. That is cheaper and less racy than adding a cache-invalidation namespace.

**The version column is deliberately not the key.** `updated_at` is the obvious choice and it is wrong by one second: its resolution on SQLite is a second, so two configuration writes inside the same second share a key. A repoint that lands in that window would keep serving the previous issuer's `token_endpoint` — and the exchange posts the *new* client secret there, a leg that runs before the `issuer`-claim check could refuse anything. A digest of the document the flow is about to use has no such window, and it has the second-order benefit that a label edit does not throw the key set away.

- **Positive TTL 15 minutes.** Long enough that a busy login hour costs four fetches, short enough that a planned rotation converges without an operator action.
- **`kid` miss forces exactly one refresh.** An ID token whose `kid` is not in the cached set triggers one out-of-band refetch, guarded by a **60-second per-provider cooldown**; if the `kid` is still absent afterwards, or the cooldown is in force, the token is refused. Without the cooldown, forged tokens carrying random `kid` values are a free amplified request generator pointed at the IdP. The cooldown is consulted **after** the currently cached set, not before: two callbacks in flight meet the same rotation, the first refreshes and arms the cooldown, and the second is asking for a `kid` the refreshed set now holds. Answering it from the cooldown would refuse a token signed by a key this replica has in hand — one failed sign-in per minute, for a rotation that has already converged.
- **Rotation is therefore a non-event.** IdPs publish the new key before they sign with it; the first token signed by a new key misses, one refetch happens, and every subsequent token hits. A retired key keeps validating until the TTL expires, which is the same 15-minute window every OIDC consumer has and is bounded by the ID token's own `exp`.
- **Stale-on-error, with a cap and a backoff.** When a refresh fails (the IdP is down, the network is out), the last good key set keeps serving for up to 24 hours and the failure is logged. Refusing every sign-in the moment an IdP has a five-minute outage would make the software less reliable than the thing it depends on. The cap exists because "serve the last keys forever" would mean a key an IdP revoked after a compromise keeps being trusted on a replica nobody restarted. The failure also stamps a **60-second backoff on its own field**, separate from the last successful fetch: without it, every start and every callback past the positive TTL re-attempts discovery *under the one cache lock* before falling back, so an IdP whose discovery endpoint times out while its token endpoint is healthy adds ten seconds to each queued request and stops the sign-in path anyway. Keeping the backoff off `fetched_at` is what stops it from quietly extending the 24-hour ceiling, which must go on counting from the last time the keys were actually verified as current.
- **Bounds:** the discovery and JWKS responses are read with an explicit `aiohttp.ClientTimeout` of 10 s (the shared session is built with `total=None`, so every call site must bring its own), capped at 256 KiB, required to be JSON, and a key set of more than 20 keys is refused. Bodies are accumulated **to end of stream** rather than taken from one `read(n)`: `StreamReader.read(n)` returns what has arrived, so a document split across two network writes comes back as a prefix that parses as truncated JSON. The same loop guards the token response, where a short read is worse than a failed fetch — the flow row is already consumed and the authorization code cannot be presented twice, so that person's sign-in is simply over. The whole cache is per-process and is dropped on restart; there is no persistence and nothing to migrate.

### The operator-supplied URL is the first SSRF surface in this product, and there is no helper to reuse

`model_sources` validates `base_url` as `min_length=1, max_length=2048` and nothing else; `require_route_or_direct_egress_opt_in` exists to force ChatGPT traffic through a per-account proxy and has nothing to do with an IdP. So the rules are written here:

- `https` only, for the issuer, the discovery URL and every endpoint the document advertises. Not a purity argument: the client secret rides the token request and the authorization code rides the browser. An IdP on plain HTTP in a compose file is served by putting TLS in front of it, which the operator has to do for the browser leg anyway.
- The URL may carry no userinfo component and no fragment; the issuer may carry no query.
- The host must not be an IP literal in a loopback, link-local, private or unique-local range, and must not be `localhost`, a `.localhost` name, or `metadata.google.internal`. This is a configuration-time check, not a connection-time one, so it does not defend against DNS rebinding — saying so is better than implying a guarantee the connector cannot make. What it does defend against is the overwhelmingly more likely case: a pasted URL, or a hostile one, aimed at the instance metadata endpoint.
- **The address is recognised in every spelling the resolver accepts.** `ipaddress.ip_address` parses only the canonical dotted quad, but `getaddrinfo` reaches for `inet_aton` first, which turns `2130706433`, `0177.0.0.1`, `0x7f.0.0.1` and `127.1` into `127.0.0.1`, and `2852039166` into the metadata endpoint. A check that refuses one spelling and connects to another is not a check, so the host is put through `inet_aton` when `ipaddress` cannot read it and the same predicates run on the result. It still resolves nothing: a name `inet_aton` cannot parse is a name, and the DNS caveat above is unchanged. This matters beyond the operator who typed the issuer — `validate_https_url` is also the gate for the endpoints the **discovery document** advertises, and `token_endpoint` is where the client secret is sent.
- **Redirects are not followed** on any of the three server-to-server fetches (`allow_redirects=False`). A redirect is exactly how a host that passes the checks above becomes one that would not.
- The discovery document's own `issuer` claim must equal the configured issuer **exactly** (the check OIDC Discovery mandates). That is what binds the returned document to what the operator typed.

**Rejected: pinning `jwks_uri` and `token_endpoint` to the issuer's origin.** It is the strongest available rule and it breaks Google Workspace, which is named in the plan: the issuer is `accounts.google.com` while the keys live on `www.googleapis.com`. A rule that forces operators to disable it for one of the four target IdPs is a rule that gets disabled. The advertised endpoints instead pass the same scheme and host checks as the issuer, and the `issuer`-claim equality above is what makes the document trustworthy enough to name them.

### `state`, `nonce` and the PKCE verifier live in a row **and** a cookie, and neither alone is enough

A cookie alone is browser-bound but not single-use: two callbacks presenting the same cookie both read it, and clearing it is a read-then-write. A database row alone is race-free but binds to nothing — anyone holding a leaked `state` could complete a flow the victim's browser started. So both, and the callback needs both:

- **Row** (`dashboard_oidc_login_flows`, primary key `state_hash`): the SHA-256 of the `state`, the SHA-256 of the `nonce`, the PKCE `code_verifier` encrypted with `TokenEncryptor`, the `purpose`, the acting account for the non-login purposes, the redirect URI as sent, and `created_at`/`expires_at` with a **ten-minute** life. The clear `state` and `nonce` are never stored: the `state` arrives in the URL and the `nonce` arrives in the ID token, so both can be hashed and compared, and a database copy that is never needed in clear is a liability.
- **Cookie** `codex_lb_oidc_flow`: the `state` sealed with the same `TokenEncryptor` the session cookie uses, `HttpOnly`, `SameSite=Lax` — **not `Strict`**, because the callback is a top-level cross-site navigation and `Strict` would drop the cookie on exactly the request that needs it — `Secure` on HTTPS, `Path=/api/dashboard-auth/oidc`, ten-minute max-age, and cleared with the same attributes on completion.
- **The consume is one statement**: `DELETE FROM dashboard_oidc_login_flows WHERE state_hash = :h RETURNING …`. Exactly one caller anywhere in the fleet gets the row. The loser and the replay get the identical uniform failure.
- **The consume happens before the token exchange**, not after. That is the point of no return: a replayed authorization code cannot reach the IdP's token endpoint twice through us, which is the property that matters, because an IdP that silently accepts a second exchange is the one that would hurt. The cost is that a token exchange which fails transiently cannot be retried and the person signs in again. That is the correct direction to fail, and for the same reason the token request is issued on the plain session and never on the retrying client.

A second start in the same browser overwrites the cookie and orphans the first row, which expires on its own; the expired rows are purged opportunistically on the next start and by the periodic cleanup scheduler's leader pass, the same two places `oauth_flow_states` is purged.

**Rejected: reusing `oauth_flow_states`.** It is the ChatGPT account-linking flow's table, with `intended_account_id`, device-code columns and a monotonic terminal-status rule that is wrong here (this flow has no terminal state, it has a deletion). Its *shape* — an encrypted verifier, a state lookup, a single-use consume — is copied; its rows are not shared.

### The redirect URI is stored, never reflected, and there is no destination parameter anywhere

`TrustedProxyHeadersMiddleware` projects `X-Forwarded-Proto` from a trusted peer but **never validates or rewrites `Host`**, and there is no "dashboard public URL" setting in the product. Building `redirect_uri` from the request is therefore Host-header injectable. It is instead a configured field, validated the same way the issuer is, additionally required to end in the callback path, and sent **byte-identically** in both the authorization request and the token exchange (RFC 6749 requires the match) by reading it from the flow row rather than re-deriving it, so a configuration edit mid-flow cannot change it underneath the exchange. Comparing the stored value against itself is the "allowlist" the brief asks for: the list has one entry and the operator wrote it.

There is **no `next`, no `return_to`, no `redirect` and no `state`-embedded destination**. Where the browser goes afterwards is derived by the server from the flow's `purpose`, from a closed set of three in-app paths. This is also how the plan's "pop-up blocked → same tab with a return URL" fallback is satisfied without a return URL: the *purpose* is what was stored, so the same-tab flow lands where that purpose implies. Every redirect this change issues is a `303` to a relative path, so there is no place for an absolute URL to appear even by accident.

### Clock skew is a named constant applied in both directions, plus one bound skew cannot buy

`OIDC_CLOCK_SKEW_SECONDS = 60`, a module constant (PRINCIPLES P2: `OAUTH_TIMEOUT_SECONDS` set this precedent, and a tolerance is not a thing an operator should tune). It is passed to `jwt.decode` as `leeway`, so `exp` and `nbf` are honoured 60 s either side, and an `iat` up to 60 s in the future is accepted — IdP and load balancer clocks differ, and a machine whose clock is a minute fast should not be unable to sign anyone in.

Skew alone would let an ID token minted hours ago be presented now if its `exp` were long, so there is a second, independent bound: the ID token's `iat` must not predate the flow row's own `created_at` by more than the skew. The flow lives ten minutes, so a valid ID token here is at most eleven minutes old regardless of what the IdP put in `exp`. The two checks answer different questions — "is this token still valid" and "is this token the one this flow asked for" — and stating them separately is what keeps the second from being quietly dropped as redundant.

### The test-login proof is two columns on the provider row, not a cookie and not a table

It has to outlive a redirect round trip, bind to the acting admin, expire in ten minutes, and be readable inside the write intent `update_provider` already holds. A cookie gives the first three and fails the fourth, and is client-held: an attacker who can set cookies sets the proof. A separate table is a migration and a lifecycle for one timestamp. So: `test_login_user_id` (FK, `ON DELETE SET NULL`) and `test_login_verified_at` on `dashboard_auth_providers`, freshness computed on read (`now - verified_at <= 600`) in the style of the qualifying-break-glass predicate, which is computed from the current row and never stored.

Four rules make it a proof rather than a formality, and each closes a hole a reviewer would look for:
- **It names an account.** Enabling requires a stamp by the *acting* account, so admin A's test cannot arm admin B's enable.
- **Writing the connection configuration clears it.** A proof that the operator reached *some* IdP must not enable a *different* one; without this rule, "test against a controlled IdP, then repoint the issuer, then enable" is a straight path to an attacker-controlled sign-in provider. Only the connection fields clear it — changing `label` or a role knob does not.
- **It names a configuration.** Clearing the stamp on a write is not enough on its own, because the callback writes it back: a `PATCH` that commits while the admin is at the IdP clears the proof and an unconditional stamp restores it against the new, untested document. So the flow row carries a digest of the document it was started against — the callback refuses a flow whose provider no longer matches, before exchanging anything — and the stamping `UPDATE` is additionally conditional on the stored blob being the one this callback read, which closes the narrower window between that read and the write. The blob compares by identity rather than by value, because the sealing is randomised; that errs toward refusing a stamp, which is the right direction for a gate.
- **A successful enable consumes it.** Otherwise the same ten-minute proof would silently re-enable a provider an operator had just turned off in an incident.

The check sits beside `_assert_break_glass_ready` inside `update_provider`'s `enabled is True` branch, under the account write intent that branch already takes before its first read. Two gates, one atomic step, one lock, and the refusals compose: a request missing both is told about the break-glass account first, because that is the one whose fix takes longer.

### Connecting an identity provider is delegating everything, so it is bounded by everything

`PATCH /api/auth-providers/{id}` already bounds its two role fields: `assert_can_delegate` against the grants of the role being handed out, so a custom role holding `security:write` but not the admin grants is refused when it points `unknown_identity_role_id` at the admin preset. That is the right rule for a lever that hands out *a role*.

The connection document is not that kind of lever. An identity provider asserts **who someone is**, and `IdentityResolver._seen` returns whichever account already owns the asserted subject, whatever its role. So a caller who may repoint the issuer can point it at an IdP they run, mint a token whose `sub` is an existing admin's subject, and be signed in as that admin — a strictly larger capability than the one the role fields refuse them, reached by a field that had no check on it at all. Turning `link_by_email` on is the same move without needing to know a subject: it widens a repointed provider from "accounts with a linked identity" to "any active account whose address you know", and the `email_verified` guard above is only as strong as the claim name, which is in the same document.

Both are therefore gated by `assert_can_delegate(principal.grants, ADMIN_GRANTS)` — the caller must already hold everything any account could hold — and only in the widening direction, so clearing `link_by_email` stays open like every other recovery path on this endpoint.

Auditing the rest of the surface for a third lever of the same reach turned one up: **`enabled`**. The role fields are bounded when they are *written*, which leaves the row nobody at this privilege wrote — and the seeded `trusted_header/default` row hands unknown identities the **admin preset** (owner decision D10). Turning a row on arms the roles it already carries, so `enabled: true` is gated on delegating the row's current `unknown_identity_role_id` and `no_match_role_id`, mirroring `role_mappings`' `_assert_may_hand_out`, which refuses the same move on the sibling surface. It runs before the break-glass and test-login gates: a caller who may not arm this row should be told that, not told to enrol a second factor first. Two levers were examined and left alone: `idp_mfa_enforced` has no reader anywhere in the product today (it waives nothing, and the step-up rules say so explicitly), and `label` is display text.

### OIDC becomes a step-up factor only for the account that has none today

`step_up_methods()` returns a list whose members are all **required** — a password account with TOTP presents both — and an empty list is the `403 step_up_unavailable` an OIDC-only admin hits. Widening `StepUpMethod` naively would make a password account do an IdP round trip too.

The rule is therefore narrow and one-directional: `step_up_methods(user, *, oidc_identity=False)` returns `["oidc"]` **only when the account holds neither a password hash nor a TOTP secret** and has an identity on an active OIDC provider. Nothing else changes. Making IdP re-authentication an *alternative* for an account that does hold a password would mean a stolen session cookie plus a still-live SSO session at the IdP is enough to change security settings without presenting anything the attacker does not already have — a downgrade wearing the word "factor".

And the re-authentication is verified, not assumed. The step-up start sends `prompt=login` **and** `max_age=0`; the callback requires an `auth_time` claim, requires it to be within `STEP_UP_MAX_AGE_SECONDS` of now (with the same 60 s leeway), and requires the returned identity triple to be one already linked to the acting account. An IdP that omits `auth_time` after being sent `max_age` is violating the specification, and the refusal is explicit rather than a silent pass — the alternative, treating a missing claim as success, makes the whole factor decorative. The proof is then minted exactly the way `POST /step-up` mints it: `su` on a re-issued session cookie for a cookie session, the generation-bound `codex_lb_step_up` cookie otherwise, audited as `step_up_verified` with `methods: ["oidc"]`.

### An OIDC session sets `password_verified`, and the local-login policy stops reading that flag

`validate_dashboard_session` admits a user cookie only when `state.password_verified` is true, so an OIDC session must set it — it is the "this cookie completed its sign-in" flag, not "this person typed a password". But `_password_fallback_principal` and the `has_password_fallback_session` branch use the *same* flag as the proxy for "a local password session" when applying `local_login_policy`. Left alone, an OIDC session would count as a local password fallback, and SSO would silently defeat `admins_only` and `break_glass_only` — the two policies that exist to close the local door once SSO is on. Both predicates therefore additionally require `state.auth_method == "password"`. This is a two-line change with a large blast radius if missed, which is why it is a requirement with its own scenario rather than a line in a diff.

There is a third reader of that flag, and it is the one that bites. `/totp/verify` treats a session issued inside the step-up window as evidence that the *password* behind it was just presented, and stamps `su` when the second factor lands — correct for a password sign-in completing its two factors in one window, and wrong for an OIDC session, which is equally fresh and equally `password_verified` with no password anywhere in its history. Left alone, an account that holds a password could sign in through SSO, enrol a TOTP secret, verify a code and hold a step-up covering every security mutation, having presented one of the two factors it is required to present. The predicate there is narrowed to a local password session by the same `auth_method` test. The account whose only credential *is* the IdP has its own path — the step-up flow below — and that path refuses any account holding a local factor, so the two rules meet without a gap.

The session is capped at `REMOTE_DASHBOARD_SESSION_TTL_SECONDS` (12 h), the constant that already means "this request is not obviously a local one", through the `max_ttl_seconds` parameter `_create_user_session` already accepts. A configured dashboard TTL shorter than 12 h still wins. No new constant, no new setting, and the cap is the honest one: an SSO session that outlives the IdP's own session is a deprovisioning hole, which is the whole reason Phase 3b exists.

### The callback is a `GET`, and no CSRF exemption is added

`DashboardCsrfMiddleware` runs before routing and rejects any non-safe `/api/` request whose `Sec-Fetch-Site` is cross-site. The callback is a top-level cross-site navigation from the IdP, so a `response_mode=form_post` callback would be answered `403 cross_site_request_rejected` before the handler existed — and the obvious fix, adding `/api/dashboard-auth/oidc/` to `CSRF_EXEMPT_PREFIXES`, would exempt a prefix that also carries session-minting routes. Choosing the query response mode makes the whole question disappear: `GET /oidc/callback` and `GET /oidc/login/start` are safe methods the middleware never inspects, and the two authenticated starts are same-origin `POST`s from the dashboard that the middleware protects for free.

The `GET` start also means the "continue with `<IdP>`" button PR-3a-2 builds is a plain link rather than a scripted `POST`. Login CSRF is not a hole here: forcing a victim's browser to *begin* their own sign-in is not an attack, and completing a flow the attacker started in the victim's browser is what the `state` cookie refuses.

Query-string credentials staying out of the logs is already true of the *application's* log lines and must stay true: `app/core/handlers/exceptions.py`, `app/core/runtime_logging.py` and the CSRF middleware all format `request.url.path`, never `request.url`. This change adds no log line that formats a whole URL — the `oauth-callback-privacy` capability exists because that mistake was made once already.

Writing no log line is not the same as no line being written, though. With default Uvicorn text access logging, `AccessFormatter` renders the full request line for **every** request, query string included, and this route's query string is an authorization code plus the flow's `state`. `UtcAccessFormatter` redacts neither today. So the redaction pass gains a rule anchored to the callback path that masks exactly `code` and `state` — the same shape as the invite-token rule that already exists for the same reason, and applied at every level rather than only at `WARNING` and above, because access logs are `INFO`. The rest of the query stays readable, including the IdP's `error`. A *refused* callback matters most: its code was never exchanged, so it is still live at the IdP, and refusals are what an operator greps the access log for.

The mask has to match the parameter the *router* sees, not the bytes: Uvicorn builds the request line from the raw `query_string`, percent-encoding intact, while Starlette builds `query_params` with `parse_qsl`, which unquotes names. `?c%6Fde=` is therefore the same request to the handler and a different string in the log, and a literal-key pattern masks one spelling of a parameter the route accepts in several. So the query is split on its separators and each name is compared *decoded* (`unquote_plus`, the same decoding `parse_qsl` applies). Values are never decoded — they are replaced whole — so nothing the redaction touched can come back out of it.

### The dialog has to be able to drive the factor the backend advertises

Making `step_up_methods` return `["oidc"]` changes a wire contract the dashboard consumes: the step-up dialog builds its request from a `password` flag and a `totp` flag, so an account with neither would have reached a dialog with no inputs, an enabled submit and an empty `/step-up` payload the server refuses — the exact dead end `step_up_unavailable` was added to remove, reintroduced in a worse shape. Widening the TypeScript literal is not enough; a backend that advertises a factor no client can present is worse than one that advertises nothing.

The connect wizard and the "continue with `<IdP>`" login button stay in PR-3a-2. This is neither: it is the one branch in an existing dialog that keeps the contract this PR's own backend change created honest. The identity-provider leg cannot be a form post, so the branch replaces the inputs with a single action that starts the flow and leaves the page, and settles the interrupted request as *not verified* first — a promise cannot survive a page load, and leaving it pending would hang whatever awaited it. Clunky in one respect, and deliberately not fixed here: the step-up callback lands on the settings card like the pre-flight does, so an OIDC-only admin stepping up from the users page comes back to the settings page. Giving each purpose its own destination is a backend change that belongs with the UI work in PR-3a-2.

### The configuration is one sealed blob, not new columns

`config_encrypted` exists. Splitting the non-secret fields into columns would let the registry read them without decrypting — but the registry does not need them: activation depends only on `enabled`, the kind and the auth mode. The fields are read on exactly two cold paths (the settings API, which decrypts to mask, and a sign-in, which decrypts to run), a Fernet decrypt is microseconds, and the alternative is six columns and a wider migration. The whole document goes in as one JSON blob, exactly as `DashboardSessionStore._seal` does for the session claims.

`GET /api/auth-providers` returns the issuer, discovery URL, client id, redirect URI and the four claim names **in clear** and the client secret as `****` plus its last four characters. The client id is public by specification (it travels in every authorization URL) and the wizard has to show it; masking it would be security theatre that makes the UI worse. No code path returns the secret in clear, logs it, or puts it in an audit detail, and the token request that carries it is never logged.

### An `oidc/default` row is seeded disabled, and there is no create endpoint

The provider settings API is `GET` plus `PATCH` and rejects unknown fields; there is no way to bring a row into existence, and the wizard needs something to `PATCH`. Adding a `POST` would open a create path for a table whose rows are meant to be fixed. Instead the existing insert-ignore seed gains a third row — deterministic UUIDv5, `enabled=False`, `unknown_identity_role_id=NULL` (the default deny of requirement 5, inherited rather than re-implemented), `no_match_role_id=NULL`, `link_by_email=False` — applied by the migration with its revision-pinned table and by `create_all` in `tests/conftest.py`, with the seed's never-update contract keeping an operator's configuration across upgrades. An install that never connects an IdP carries one disabled row and behaves exactly as before.

### `provider_active` gets an explicit branch, because falling through would enable OIDC in `disabled` mode

`provider_active` returns `False` for any kind not in `_IMPLEMENTATIONS` and otherwise falls through to `return True` for everything that is not `trusted_header`. Registering OIDC would therefore make an enabled row active in **every** `dashboard_auth_mode`, including `disabled` — an install that has explicitly turned dashboard authentication off would grow a sign-in flow that mints account sessions and provisions accounts. OIDC is active in `standard` and `trusted_header` mode and never in `disabled`.

### `sub` is not case-folded, and the `th-` slug prefix is not renamed

The trusted-header provider case-folds its subject because two proxies spelling one person differently must not become two accounts. An OIDC `sub` is case-sensitive by specification and opaque; folding it would merge two distinct subjects at an IdP that issues both cases, which is worse than the duplicate it would prevent. The subject is taken verbatim, bounded by the same 512-character column width, and an empty one is refused.

Verbatim means **not trimmed either**. Trimming is case-folding one character over: an IdP free to issue `alice` is free to issue ` alice `, and an identifier the system normalises before looking it up is an identifier two people can share. Emptiness is checked against the stripped value and length against the raw one, but neither check rewrites what is looked up.

`slugify_subject`'s empty-result fallback is `th-<8 hex>` — trusted-header flavoured, and applied to every provider. An OIDC `sub` that slugs to nothing (an all-punctuation opaque identifier) gets a `th-` username. Parameterising the prefix would mean modifying the canonical "Just-in-time usernames" requirement and forking a rule three providers share, to change a cosmetic prefix on a username nobody types. It is left alone, deliberately, and written down here so the next reader knows it was a decision.

### An unverified e-mail is dropped, not carried

`email_verified: false` means the IdP is telling us the person has not proven that address. The resolver uses `identity.email` for four things: `link_by_email`, the new account's e-mail, `email_domain` role-mapping rules, and the re-evaluation that re-runs those rules on every later sign-in of a mapping-managed account — the last two are role escalations if the address is self-asserted (claim the company domain, match the catch-all rule, get the role). The provider therefore carries **no** e-mail when the claim is present and is not an explicit affirmative.

"Present and false" is the tempting reading and it fails open. `email_verified` is a boolean in the specification and a string at several IdPs in practice — Google's documented ID token carries `"true"`, Apple documents string-or-boolean, Cognito emits strings for attributes it maps from an upstream provider — so a test for the JSON `false` lets `"false"`, `0` and `"no"` straight through. The rule is inverted instead: present means the value must be `true` or the string `"true"` case-insensitively, and anything else present is false. The string spelling has to be *accepted*, not just tolerated, because testing `is True` would drop the address of every legitimately verified Google and Apple user. Every other claim in the module already type-checks and fails closed; this was the one line that did not. The cost is that the `login_failed` audit row for such an identity shows a null e-mail, which is a real loss of diagnostic detail; the alternative is a field on `ExternalIdentity` that only one provider sets, forking a frozen dataclass three call sites construct. When the claim is absent entirely — many IdPs omit it — the e-mail is carried, which is safe because `link_by_email` is off by default and `email_domain` rules are something an operator writes deliberately.

### Failures are uniform, and the one distinction that exists is required

Every callback failure that is not "this identity has no account here" ends the same way: `303` to a fixed in-app path with no detail, one `login_failed` audit row with `reason: oidc_login_failed` and a coarse `stage`, and nothing from the IdP's `error_description` reflected anywhere. An unauthenticated caller cannot tell a bad `state` from a bad `nonce` from a failed exchange.

The unprovisioned identity does land somewhere else — `/auth/pending` — and that is not a leak to fix but the behaviour the plan requires: the person just authenticated at the company IdP, and telling them "you are not set up here yet" instead of "something went wrong" is the entire point of that screen. Rate-limit refusals answer `429` with `Retry-After` as JSON rather than a redirect, because that is a machine condition and a redirect loop is worse than an honest status code.

Rate limits follow the invite precedent: a per-address bucket on each public route, plus a second per-`state` bucket on the callback keyed on the hash, never the value — the same shape as `invite_accept_token`. A success clears the per-`state` bucket only; the per-address ceiling is left to expire, because clearing it on success would hand the endpoint's only ceiling to anyone who can complete one sign-in.

## Risks / Trade-offs

- **A new dependency in an authentication path.** `pyjwt` is widely deployed and its only new transitive dependency is already ours, but it is a third party in the most sensitive code in the product. Mitigated by calling it with an explicit key and an explicit algorithm list derived from the key rather than the token, so the library's own defaults are never the thing standing between us and an algorithm-confusion attack.
- **Stale-on-error means a revoked key stays trusted for up to 24 hours** on a replica whose refreshes are failing. The alternative is an IdP outage locking every SSO user out. The cap and the 15-minute happy-path TTL are the compromise; an operator who has revoked a key after a compromise disables the provider, which is never gated.
- **Configuration-time host validation does not stop DNS rebinding.** Doing it properly means resolving and pinning the address before connecting, which the shared connector does not support. Stated rather than implied, and the far more likely mistakes — a pasted metadata URL, a redirect into the private range — are covered.
- **Consuming the flow before the exchange makes a transient IdP failure cost a full restart of the sign-in.** Accepted: the property being bought is that we never exchange one code twice.
- **One Fernet key protects the client secret, every session cookie, every account token and now the flow verifiers, and there is no rotation path anywhere in the product.** This change adds a fourth kind of value to that key without improving the situation. Worth writing down here rather than discovering during a key-rotation incident; a rotation path is its own change.
- **`step_up_methods` gains a parameter**, and its return value is part of the wire contract (`details.methods` on the 403, and `step_up.methods` on the session response). The default keeps every existing call site's behaviour identical, and the new value appears only for an account that could not step up at all before.
