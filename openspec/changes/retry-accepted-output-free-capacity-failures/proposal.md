# Retry Accepted Output-Free Capacity Failures

## Why

The bounded pre-visible retry only covers failures that arrive *before* upstream accepts a response. Native Codex traffic also fails after acceptance: upstream delivers `response.created` and `response.in_progress`, produces no output, and then terminates the turn with a capacity error (`server_is_overloaded`, `overloaded_error`, `model_at_capacity`, or the "selected model is at capacity" message) or drops the transport. Verified on `main`: the shared classifier (`_websocket_precreated_retry_error_code`) returns `None` as soon as `response_id` is set, and the transport-close eligibility (`_websocket_request_can_replay_before_visible_output`) caps the created-only case at one counted event, so created + in_progress is refused. The client gets a terminal error for a turn that produced nothing, and the agent stops mid-task.

This change takes over PR #1384 by Darafei Praliaskouski with the owner's narrowed scope: a native-Codex **HTTP-bridge** request that upstream accepted and then failed output-free is replayed once on another account while the client observes a **single** response lifecycle. The direct SSE initial-EOF retry from #1384 (which would reverse the #1389 fail-closed boundary) and anchored abrupt-close replay without an idempotency proof stay out of scope, and so does the direct WebSocket surface (see Non-Goals).

## Scope

- **In scope: the HTTP responses session bridge.** Every native Codex bridge request (`_REQUEST_TRANSPORT_HTTP` request state) gets the accepted output-free replay described below.
- **Out of scope: the direct `/backend-api/codex/responses` WebSocket surface.** Its accepted turns keep the behaviour they had before this change (see Non-Goals and the follow-up section).

## What Changes

- Classify one accepted, output-free capacity terminal (`error` / `response.failed` with a capacity code or the selected-model capacity message, naming no other response and reporting no output items or billed output tokens) as replayable on the HTTP bridge. Quota and rate-limit codes after acceptance stay fail-closed.
- Widen the bridge's pre-visible transport-close replay eligibility from "created only" to "accepted lifecycle only" (`response.created` plus optional `response.in_progress`, no output marker, no pending tool call, no buffered reasoning prelude). The shared predicate keeps the created-only rule for direct WebSocket request states.
- Reuse the existing single-lifecycle mechanism (`replay_downstream_response_id` + created suppression + id rewriting) and extend it with `response.in_progress` suppression, so the client sees exactly one `response.created`, no duplicated `response.in_progress`, and every later frame under the id it already reads. The identity is captured **before** `response_id` is cleared; clearing first is the ordering hazard that made #1384's own tests observe two created ids.
- Re-claim the session response-create gate non-blockingly before an accepted replay owns the pre-created identity (a contended gate forwards the upstream terminal unchanged), mark shared work admission for re-acquisition, and exclude the failing account so the resend lands on another account when the body is account-neutral. An anchored accepted turn whose fresh body cannot leave the anchor's owner (client-supplied anchor, account-scoped upload) is re-sent as the anchored body to the account that accepted it.
- A protocol-invalid binary frame never replays an accepted turn; only a terminal transport message (close or error) does.
- One surface predicate, `_accepted_lifecycle_replay_enabled` (`support.py`), gates every accepted-replay entry point on the request state's transport. It is true for bridge states and false for direct WebSocket states, so the WebSocket surface can be re-enabled in one place; the WebSocket-side accepted-replay code paths (classifier delegation, exclusion decision, health deferral, other-pending re-read) stay in the tree behind it.
- Shared fixes that also cover pre-created and created-only replays stay on **both** surfaces: the fresh-body install reconciles the owner pin with the body it sends (`_install_fresh_replay_body`: a proxy-injected anchor's body pin is released, an account-bound body or a client-supplied anchor keeps its owner, a turn-state owner survives as a session pin); the pre-created `retry_safe_owner_replay` branch on the direct WebSocket path decides its exclusion with `_websocket_accepted_replay_can_switch_account` instead of unconditionally excluding an owner the reconnect hard-requires; websocket idle keepalives carry the client-visible response id; the direct WebSocket relay records model output (`upstream_model_output_seen`) like the bridge relay.

## Non-Goals

- **Direct WebSocket accepted replay.** Seven verification rounds kept surfacing owner-switch edge cases specific to the WebSocket reconnect: the exclusion the replay adds collides with owners that are not request-state pins but are resolved at selection time (a raw legacy `CODEX_SESSION` row, `hard_affinity_saturated` until the connect budget), with turn-state pins that the fresh-body install used to clear, and with client-supplied anchors. Per the owner's direction the WebSocket surface is de-scoped: accepted (`response.created`[+`response.in_progress`], output-free) direct WebSocket turns behave exactly as before this change -- an output-free capacity terminal is forwarded unchanged and an abrupt close after `response.in_progress` fails closed as `stream_incomplete`, while the created-only transport-close replay keeps its rules (one counted event, no widening to two) and never excludes the account. Tracked as the follow-up under issue #2126.
- The direct SSE initial-EOF retry and anchored abrupt-close replay without an idempotency proof (from #1384).

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `responses-api-compat`: accepted output-free capacity failures are replayed within a single response lifecycle on the HTTP bridge; the HTTP bridge model-capacity wait applies before any downstream-visible *model output* rather than before any response event; direct WebSocket accepted turns keep their pre-change fail-closed handling.

## Impact

- New helper module `app/modules/proxy/_service/http_bridge/accepted_replay.py` (accepted-state predicate, terminal classifier, output-evidence check, gate re-claim, replay staging).
- `app/modules/proxy/_service/support.py` (surface predicate `_accepted_lifecycle_replay_enabled`, lifecycle-only predicate, `suppress_next_in_progress_downstream`, replay eligibility with the created-only fallback for direct WebSocket states), `app/modules/proxy/_service/websocket/helpers.py` (classifier delegation gated by surface, identity-preserving replay preparation, owner-pin reconciliation, dormant WebSocket exclusion/health helpers), `app/modules/proxy/_service/http_bridge/upstream_events.py` (staging at the capacity branches, `in_progress` suppression) and `app/modules/proxy/_service/websocket/mixin.py` (gated accepted-replay sites, model-output bookkeeping, visible-id keepalives, pin-aware pre-created owner switch), `app/modules/proxy/_service/http_bridge/request_submit.py` (gate re-claim and other-pending guard on the transport-close path).
- No API, schema, migration, dependency, configuration, or dashboard changes. No ceiling file (`service.py`, `load_balancer.py`, `http_bridge/mixin.py`, `streaming/mixin.py`) grows.

## Known Limitations

- The HTTP bridge does not track a downstream `sequence_number` watermark, so when the replay's suppressed prelude is shorter than the failed attempt's, one SSE `sequence_number` may repeat on the bridge surface. Renumbering rewritten frames is a follow-up.
- A client that later anchors explicitly on the visible id receives upstream `previous_response_not_found` and enters the existing continuity recovery; proxy-injected anchors use the completed upstream id and are unaffected (same as the existing created-only replay).
- Excluding the failing account turns a transient overload in a single-account pool into a selection failure for that request (parity with the bridge's existing pre-created replay).
- **Open (bridge, hard session keys):** an accepted output-free replay on a hard bridge session key (`session_header`/`thread_header`) still excludes the account that accepted it even when the session's affinity resolves a raw legacy hard `CODEX_SESSION` owner (`request_submit.py`, `fresh_hard_request_account_switch_allowed` has no accepted check; `_reconnect_http_bridge_session` runs without `require_same_account` unless the close code was 1011). Selection then fails `hard_affinity_saturated` and the reconnect loop sleeps until the request budget before the 503 -> 502 `stream_incomplete`; `main` failed that shape closed immediately. The bridge analogue of the WebSocket owner-switch class; candidate fix: refuse the fresh-hard account switch for an accepted lifecycle when `_websocket_affinity_may_resolve_hard_owner(session.affinity)` and reconnect with `require_same_account=True`, or treat `hard_affinity_saturated` with the accepting account as the only exclusion as a same-owner retry (the SSE pattern in `streaming/retry.py`).
- HTTP bridge transport close with an accepted request and a pre-created sibling that still holds the session gate: `main` retried the pre-created sibling alone and left the accepted request bound to the dead upstream until the stale pending sweep; both now fail closed promptly with `stream_incomplete` because the accepted request is retryable too and the transport-close retry only ever reconnects a sole retryable request.
- The eventless pre-response watchdog stays disarmed for the replay attempt because `latency_response_created_ms` is already recorded (parity with the existing created-only replay); the generic receive timeout still bounds a silent replacement socket.

## Direct WebSocket follow-up (#2126)

The WebSocket half of #2126 stays open. Re-enabling it is a one-predicate change plus the design decision that blocked it:

- **Switch:** make `_accepted_lifecycle_replay_enabled` (`support.py`) return true for `_REQUEST_TRANSPORT_WEBSOCKET` request states. Everything it gates is already in the tree: the classifier delegation in `_websocket_precreated_retry_error_code`, the accepted branches of the direct WebSocket text path (staging via `_stage_websocket_request_state_for_replay(surface="websocket")`, owner-switch prep, exclusion via `_websocket_accepted_replay_may_exclude_account`, settlement-deferred health via `_record_or_defer_websocket_accepted_replay_health`), the transport-end exclusion in `_process_upstream_websocket_transport_end`, the other-pending re-read under the pending lock before the classifiers run, and the lifecycle-only widening of `_websocket_request_can_replay_before_visible_output`. Their unit tests stay in `tests/unit/test_proxy_utils.py` (predicates, install, health helper); the surface tests there and in `tests/integration/test_proxy_websocket_responses.py` currently assert main parity and must be flipped back to replay assertions.
- **Open design point:** the direct WebSocket reconnect must not exclude an owner that is resolved at selection time. `_websocket_affinity_may_resolve_hard_owner` refuses the exclusion for every `CODEX_SESSION` / legacy-lookup affinity, which makes the account switch soft-row-only (the health penalty steers a soft row away; a hard row reconnects to its owner). The preferred completion is an SSE-style same-owner retry in `_connect_proxy_websocket` when selection reports `hard_affinity_saturated` and the failing account is the only excluded id (`streaming/retry.py` pattern), which lets the exclusion be decided from the resolved row instead of the policy shape.
- **Contract to preserve when re-enabling:** the requirement "Direct WebSocket replay never mixes numeric response sequences" (a sequenced prelude is never replayed), the other-pending guard evaluated under the pending lock after the thread-affinity await (an accepted request no longer holds the session create gate), and the single-lifecycle guarantees of the bridge requirement.
