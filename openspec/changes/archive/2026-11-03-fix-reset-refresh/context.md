# Reset recovery

The upstream usage endpoint can keep returning an exhausted window after a reset credit is spent. A minimal request pinned to the affected account can wake that limiter, as documented in Soju06/codex-lb issues #676 and #677. Recovery first refreshes usage, avoiding that extra request when a new window is already visible. Otherwise, an exhausted sample permits one wake followed by one refresh. The shared transport resolves the account's proxy route and never substitutes another account or silently falls back to direct egress when route resolution fails.

Successful credit redemption is an explicit reset signal, but it is not sufficient to make an exhausted account selectable. Corresponding samples must show lower usage below exhaustion and a reset deadline advanced by at least 60 seconds. All reported applicable windows must be available, and an omitted, still-exhausted current window prevents early recovery. Natural recovery additionally matches the previous sample to the persisted blocking boundary, preserving an unrelated short throttle. Secondary-only accounts can recover without a primary window. For example, a weekly account whose usage changes from 100% used to 0% used with a new weekly deadline can leave the old cooldown after an accepted redemption.

The status update retains the original status, reason, deadline, and block-marker comparison. Integer block markers must predate the recovery operation's second so a newer failure cannot reuse an identical comparison tuple. An explicit operation waits at most one second when necessary, rereads the account, and starts new evidence collection. Usage snapshots record fetch start rather than completion. Runtime reconciliation accepts only available evidence newer than its block and last error, removes the attributed quota contribution to backoff, and preserves unrelated transient errors, leases, and ordinary health transitions. The accounts endpoint uses a copied runtime snapshot for the same replica's quota badge; it does not claim model-specific or API-key-specific eligibility.

Natural stale rollover uses the existing durable warmup claim table under a separate reset-recovery namespace. A claim is committed before network activity and remains consumed on failure. These claims are excluded from ordinary warmup history and scheduling. Repeated ticks and concurrent workers therefore do not repeatedly probe the same account/window boundary.

This change targets v1.24.0. It does not deploy the running service or change routing strategy, sticky affinity, or proxy bindings. Stronger cross-replica timestamp fencing assumes comparable, non-regressing clocks and updated usage writers; a mixed-version rollout cannot establish fetch-start provenance for rows written by an older peer. Current upstream main requires a separate forward-port.

Verification used Python 3.13, synthetic credentials, and stub upstream responses. The full backend suite was completed with four workers. Two dependency-absence assertions remain reproducibly failing on both this patch and untouched v1.24.0; the test intercepts builtins.__import__ while the implementation calls importlib.import_module. A full-run logging suppression option invalidated one logging assertion, which passes with logging enabled. One subprocess-readiness failure did not reproduce on either version in targeted reruns. None of these checks establishes live upstream or deployed behavior. The strict change validator passed; eight existing main-spec validation failures are byte-for-byte identical to baseline validation results.
