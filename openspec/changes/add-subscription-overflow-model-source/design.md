## Context

Design source: issue #2123 (subscription-exhaustion overflow to a designated model source; design §3 constants, §9.1 pin schema, §12 zero-cost-when-disabled budget, §14/§16 rollout). The rollout is staged — schema (this stage), inert settings designation and preflight, pin repository, routing, dashboard, docs — so the Alembic graph stays single-headed while the behavioural stages are reviewed. Every later stage extends this change folder.

## Decisions

1. **`dashboard_settings.subscription_overflow_drain_until` is a naive `DateTime`.** Every `dashboard_settings` timestamp is naive UTC and the application compares them with `utcnow()` (naive UTC). The drain deadline is arithmetic on that clock (`now + 7 d pin idle TTL + 21 d tombstone grace + 1 d = now + 29 d`). Startup drift detection compares `timezone=` exactly, so ORM and DDL both declare it naive.
2. **`model_source_pins` timestamps are `DateTime(timezone=True)`.** Pins follow `file_account_pins`: the database clock is authoritative for expiry and tombstone comparisons, so the pin repository (later stage) can use dialect-native `now()` clauses like `FileAccountPinRepository`.
3. **No foreign key from `source_id` to `model_sources`, no `Enum` for `kind`.** Rows must outlive a deleted source for the drain window instead of cascading away, and `kind` (`thread` | `anchor` | `bounce`) is a namespaced discriminator whose values are owned by the routing stage, not the schema.
4. **No foreign key from `subscription_overflow_source_id`.** Mirrors `single_account_id`: a dangling id is "off" by definition. Deleting the designated source clears the setting in the same transaction (settings stage).
5. **One plain index on `purge_at`, created inside the migration transaction.** The table is created empty by the same revision, so `CONCURRENTLY` buys nothing. The index step is guarded independently of the table step so a pre-existing table (partial dump, out-of-band creation) still receives the index; on PostgreSQL an existing invalid same-named index is dropped and rebuilt rather than accepted by name.
6. **No `server_default`, no backfill, no seed rows.** Both settings columns are nullable and NULL means off / no drain armed; the pin table starts empty.

## Decisions (WP-B: designation, preflight, drain, dashboard)

7. **Tri-state designation via `model_fields_set`, independent of `single_account_id`.** `subscription_overflow_source_id` follows the settings API's absent/null/value convention. The repository clears it through an explicit flag rather than reusing the `single_account_id` line, whose NULL write is coupled to `routing_strategy`; the overflow designation never touches or depends on the routing strategy.
8. **Drain deadline is arithmetic in the same row update.** Clearing (non-NULL → NULL) writes `drain_until = now + PIN_IDLE_TTL (7 d) + PIN_TOMBSTONE_GRACE (21 d) + 1 d`; designating (NULL → non-NULL) writes NULL; a same-state write or a switch between sources leaves it untouched. The deadline is read-only on the API. The three constants live in `app/modules/settings/subscription_overflow.py`; the pin repository (WP-C1) imports them so the 29-day window is defined once. The settings read contract also carries the derived `subscription_overflow_pins_expire_by = drain_until − PIN_TOMBSTONE_GRACE − 1 d` (the clear time plus `PIN_IDLE_TTL`, computed at response time by `resolve_pins_expire_by`): the drain cap (CL-3) lets no pin outlive it, so it is the date the dashboard's drain notice shows and is gated on, whereas `drain_until` only bounds the tombstone lookup window and would overstate by 22 days how long conversations keep working.
9. **Eligibility = kind `openai_compatible` and `supports_responses`; enabled-ness is not validated.** Disabling the source is a kill switch, so a disabled source may stay designated. Only a *new* designation is validated; the dashboard's full-payload saves re-send the current value without re-validation, so a source that later lost Responses support does not block unrelated saves (the preflight reports it as a blocker instead).
10. **Preflight is a separate `GET`, not part of the `PUT` response.** The design text says the report is "also returned by the update"; coupling the settings PUT to the model registry and the pin table would make every settings save pay for the report. The dashboard calls the GET on selection and after each save (the update mutation invalidates the preflight query), so the operator experience is identical. The endpoint requires dashboard write access: it enumerates the source catalog and API-key scoping, which a read-only guest must not see.
11. **Preflight semantics.** `missing_models` lists the registry's subscription slugs that could overflow (not Responses-Lite / code-mode) and are not enabled on the source; a listed source model that maps to a Lite/code-mode registry slug, or to no registry slug at all, is reported as `never_overflows` with a reason and carries only that exclusion warning. Everything else — undeclared Codex tool types, vision, streaming, pricing, context window smaller than or missing versus the registry — is a warning; only the two eligibility checks are blockers.
12. **Delete clears in the delete's transaction.** `ModelSourcesRepository.delete` issues the single commit, so the settings clear rides on it and a designated-but-deleted source cannot persist; `DashboardSettings.version` (the version_id_col) still surfaces a concurrent settings save as `409 settings_conflict`. The settings cache is invalidated (bumping the cross-replica namespace) only after the commit and only when something was cleared.
13. **Inertness is mechanically enforced.** `tests/unit/test_subscription_overflow_inert.py` asserts that nothing under `app/modules/proxy`, `app/core`, or `app/modules/api_keys` mentions the designation, the pin table, or the helper module, and that only the settings and model-source dashboard modules (plus the ORM/migration) do. The request path therefore still performs exactly one warm `SettingsCache.get()` and reads none of the new columns (invariant I9). WP-C1/WP-C2 relax the ratchet together with the routing spec deltas.

## Decisions (WP-C1: source-dispatch owner and direct-routing hardening)

14. **One owner, one latch, one row.** Every Responses request forwarded to a model source is owned by a `SourceDispatch` created right after the API-key reservation; `finish()` is the only place the source connection is closed, the reservation settled or released, the admission claims released, the result counted and the request-log row written. Each step is latched on its own and awaited with cancellation deferred, so a failing release never skips the row and a client that leaves mid-cleanup never interrupts it. `abandon()` is `finish("cancelled", <stage>)`; `finalize_transport()` runs from `SourceStreamingResponse.__call__`'s `finally` so an ASGI disconnect before Starlette iterates the body still ends in exactly one disposition. The reservation primitives (`_settle_source_reservation`, `_release_reservation`) stay in `api.py` and are injected into the owner: the route tests patch them there, and the owner module must not import `api.py`.
15. **Settlement is the outermost body layer for every key.** The limited-key buffered branch for Responses is gone; limited and unlimited keys stream live through `settlement_stream(wrapper(body))`. The layer that owns the reservation is therefore the first to observe a cancellation or `GeneratorExit`, and "aclose() on a never-started generator skips its finally" now only affects inner layers that own nothing. Limited keys settle at an estimate (admission input estimate or 8192; `max(2048, delta_chars // 4)` output) when usage is missing or the client cancels after the first output item; a cancel before it releases; a stream the source ends with `response.failed`/`error` is an error and releases (the public wrapper relays the failure and ends normally, so the terminal kind is classified before settlement). Estimates are never written to the row as usage.
16. **The bulkhead lands with C1, before the reservation.** `max_concurrency` was declared but never enforced for direct routing. `try_claim(source)` runs before `_enforce_request_limits`, so a saturated source answers `503 model_source_busy` (+`Retry-After: 1`) with no reservation and no row; the claim is handed to the owner (`transfer_to`) and released by exactly one latch. The WP-C2 breaker fills the `trial` slot (`TrialClaim.settle(result)`); with `trial=None` a trial result records nothing.
17. **Owned concurrency for the raced open.** The source open runs as a task the watch always cancels and awaits (`_await_task_deferring_cancellation`); the open coroutine assigns `owner.stream` itself before completing, so a stream that completes into a leaving caller is closed by `abandon()` rather than by garbage collection. Stall evidence is "no frame for 10 s" — a slow-prefill source that already produced `response.created` is never a stall.
18. **Metric and attribution names keep the inertness ratchet strict.** Nothing under `app/modules/proxy` or `app/core` may spell the designation or the pin table yet, so the dispatch counter is `codex_lb_model_source_dispatch_total{kind,status}` with an opaque `kind` (`direct` today; WP-C2 supplies its own), the request-log `source` is a parameter (`request_log_source`, default `model_source`), and the live-pin gauge is `codex_lb_model_source_live_pins{kind}` rather than the design's `..._pins_live` (the `model_source_pins` substring is a ratchet identifier under `app/core`). The pin-failure error codes are parameters too (`pin_failure_error_code`, `pin_unverified_error_code`); direct routing never arms a pin intent.
19. **Honest pre-body errors, generic credentials.** Pre-open `ModelSourceForwardingError`s keep the source's status and sanitized envelope and now carry the source's `Retry-After` header; the 401/403 recode to `502 model_source_credentials_error` is a transport-package decision applied to Responses dispatch only (chat completions keep passthrough). Dispatch log lines carry stage names, ids, status codes and durations — never the source's error message.
20. **`context` is optional on the route helper.** `_source_responses_response(..., context=None)` reads the scheduler, clock and cancel-safe cleanup owner from `ProxyContext.service`; the direct-call tests that build a bare `Request` keep working with the real defaults.

## Decisions (WP-C1 integration: projection gate, transport, pins, probe)

21. **Portability verdict order and tool vocabulary.** `responses_payload_is_provider_portable` evaluates the design's steps as 3 → 5 → 4 → 6 → 1/2 → 7. The account-neutral replay predicate (step 1) subsumes the tool and item vocabulary, so evaluated first it would report every undeclared tool type, `namespace` tool and unsupported item as `not_portable_history` — the only reason that earns the "start a new conversation" hint, which would be false for bodies a fresh conversation reproduces identically. Step 4 defers history-class items (`reasoning`, `compaction`, `item_reference`, account-scoped hosted inputs, `mcp_*`) to the history check; bare content parts and unknown item types are `not_portable_items`. Step 5 accepts `function`, predicate-neutral declared types (`custom`, `web_search[_preview]`, strict predicate shapes) and the closed stateless Codex set `{apply_patch, shell, local_shell, tool_search}` in exactly `{type, description?}` shape; hosted types (`code_interpreter`, `file_search`, `mcp`, `image_generation`, `computer_use_preview`, …) and `namespace` are `not_portable_tools` even when the operator declared them, because their declarations carry container / vector-store / connector state that belongs to the subscription account. The classification view drops exactly `{max_output_tokens, prompt_cache_retention, safety_identifier, temperature, top_p, user}` (pinned against `_RESPONSES_PAYLOAD_FIELDS_WITH_DEDICATED_VALIDATION`), and the view builder declines telemetry fields loudly: WP-C2 strips first (`strip_service_tier=True` for overflow), then builds the view. Fixtures are synthetic (shaped after `responses_lite.rs` / `client.rs`); captured bodies remain a WP-C2 verification item.
22. **The shared replay predicate fails closed instead of raising.** `responses_payload_is_account_neutral_fresh_replay` and its helpers raised `TypeError` on malformed nested values the request model admits (`tool_choice: {"type": []}`, list-typed `role`/`phase`/part `type`, list-typed top-level items). Every set membership on a JSON value now goes through a totality helper and list-typed items are declined before delegating; well-formed inputs classify exactly as before, malformed ones return `False` instead of a 500 on the subscription affinity path. `extract_input_file_ids` in `app/core/openai/requests.py` is still not total for list-typed item types (guarded from `replay_safety.py`; other callers untouched — owner item).
23. **Idle cap on the scheduler seam, not `sock_read`.** aiohttp arms `sock_read` from request send, so a configured idle window below 20 / 30 s would pre-empt the header and first-frame deadlines. The idle bound is one `scheduler.wait_for(next_chunk, min(stream_idle_timeout_seconds, 300))` per chunk after the first frame; `sock_read` stays unset and aiohttp's own `total` expiry mid-stream is re-raised untagged (existing behaviour). `_open_source_stream` returns the first chunk and is shared by chat streams, so the deadlines and the dedicated connector apply to every source open while the 401/403 recode is a Responses-only keyword (`recode_credential_failures`). `forward_responses` keeps its contract signature (no scheduler kwarg) and bounds only connect + total.
24. **An oversized frame is content.** A Responses frame that outgrows the usage parser's 1 MiB buffer cap cannot be a bookkeeping envelope (`response.created` / `in_progress` / `queued`), and its truncated remainder never parses, so it can no longer be classified by its event type. The parser marks `first_content_seen` when the cap trips: with a pre-content hook armed the hook runs before any byte of the frame is released (I11: delivered ⇒ pinned) and the withheld buffer stays bounded by the cap instead of the whole stream. Direct routing arms no hook and is unaffected; the usage carried by such a frame was already lost before this change (limited keys now settle at the estimate instead of failing closed).
25. **Pin writes: acquisition in the caller's task, statement in an owned task; bounce rows never touched.** anyio locks are task-bound, so `PinWriteExecutor` acquires the writer section / connection checkout in the caller under `scheduler.wait_for(10 s)` (timeout or any non-cancellation failure before issuance → `not_written`; a caller cancellation before issuance propagates), then runs statement + COMMIT to completion in an owned task with cancellation deferred and re-raises a deferred cancellation only after the outcome is logged. `touch` slides live thread/anchor rows only; bounce rows (`expires_at = purge_at = min(now + 60 s, drain cap)`) are excluded in SQL and tombstones are never revived. The executor never populates `PinCache` (WP-C2 puts after `lookup` / `written`); `delete_durably` invalidates before and after. Thread pins accept only the `thread_only` selection key (the `process_thread` form and raw ids are rejected) and are never namespaced by API key or session.
26. **Retention tick no longer gates on the opt-in windows.** `DataRetentionScheduler._prune_once` runs the pin purge on every leader-gated tick even when both retention windows are unset (pins carry their own `purge_at`): one `try_acquire`, one keyed batched `DELETE` on the database clock, plus one `MAX(purge_at)` read only while a drain is armed (WARN `model_source_pins_drain_invariant_violated` when it reaches `drain_until`). `run_retention_pass` gains the `model_source_pins` key; the opt-in tables stay gated. The inertness ratchet allows `app/core/retention/job.py` to name the pin table (pin identifiers only, never the designation) and pins the pin module's importers to `{app/core/retention/job.py, app/modules/proxy/source_dispatch.py}`.
27. **Read-only exhaustion probe through `observe_only`; admission body extracted.** `ProxyService.check_opportunistic_admission(..., service_tier=None, observe_only=False)` and the load balancer's method gained both keywords. `observe_only=True` builds selection states from a detached runtime snapshot (per-entry copies, stale leases expired on the copy with the shared `apply_lease_release` math) with no runtime lock, no reclaim or prune of live entries, no health-tier refresh and no version bump, so the probe never changes what Force Probe settlement or the next selection sees; `service_tier` flows to `_load_selection_inputs` for parity with selection. `probe_pool_usage_exhaustion` answers `PoolExhaustion` iff `error_code == usage_limit_reached` (I5). Because `load_balancer.py` sat at its line ceiling, the former method body moved verbatim to `_load_balancer/opportunistic_admission.py` (3021 → 2955 lines) and the account-scope rule to `_service/support.py::opportunistic_admission_account_scope` (service.py 2598 → 2565); the delegation costs two frozen-dataclass allocations per admission check (~2 µs, no await, no I/O) on the subscription path.
28. **A pre-existing drain-strategy divergence is excluded from the trigger, not fixed.** The parity property surfaced that under `sequential_drain` / `reset_drain` / `single_account` the opportunistic and foreground selectors draw from different budget subsets and return the subset's answer directly, so a pool mixing an available additional-quota-scoped account (exempt from the exhaustion predicate) with a usage-exhausted account is called exhausted by foreground selection and not by the probe's selector. It affects only additional-quota-gated models with mixed exempt and non-exempt plans under drain strategies, predates this change, and belongs in `_load_balancer/sticky_selection.py`. Making the probe evaluate the foreground subset there was rejected: the observation mode must answer exactly as the live admission check (account-routing requirement), a new budget-subset knob would thread through four layers with `load_balancer.py` at its line ceiling, and the foreground subset is itself state-dependent (the sticky budget-pressure branch applies the secondary threshold), so equivalence could not be proven cleanly. `probe_pool_usage_exhaustion` therefore takes the caller's dashboard-settings snapshot (the object `opportunistic_admission_account_scope` already reads) and declines for the drain family before any selection work: `None`, one `codex_lb_pool_exhaustion_probe_declined_total{reason="drain_strategy"}` increment and an INFO `pool_exhaustion_probe_declined` line naming the strategy. Drain strategies never trigger overflow in v1; WP-C2 must not bypass the decline. The former strict xfail is a positive test of the decline (all three strategies, selector never consulted) plus a premise test asserting the divergence still exists, so a selector fix re-opens the decision instead of silently widening the trigger.

## Decisions (WP-C1 review fixes)

29. **The admission budget estimate runs under the route-helper latch.** `estimate_api_key_request_usage` serializes the body and raises `UnicodeEncodeError` on a lone surrogate inside the first ~8 KiB; computed between `try_claim` and the `try` that releases unowned claims, the raise left the bulkhead slot claimed forever (one malformed request per slot saturated a `max_concurrency` source on that worker, I13). The estimate now sits inside the latch, so every failure between the claim and `transfer_to` releases the slot; the 500 itself is unchanged and pre-dates this change.

30. **The EOF tail is a frame.** `SourceStreamUsageParser` only parsed blank-line terminated frames, while the proxy's own event-block reassembler (and every SSE client) accepts a final record closed with a single newline. With a pre-content hook armed, a `response.completed {output: [...]}` tail therefore reached the client without the hook (I11 bypass); without a hook its usage and terminal kind never reached the holder. `finish()` parses the unterminated tail at EOF before the withheld bytes are classified and released; a record cut mid-JSON (and a truncated oversized remainder) parses to nothing, which is still "nothing delivered".
31. **Withheld bytes are bounded on their own.** Decision 24's "bounded by the cap" only held for one unterminated frame: every complete bookkeeping frame (`response.in_progress` / `queued`, comments) cleared the parser buffer and was appended to the withheld list, so a noisy source could grow it for its whole total budget (600 s default). `SOURCE_STREAM_WITHHELD_CAP_BYTES` (2 MiB, twice the parser's frame cap so a single oversized frame reaches the content classification first) fails the stream closed with `502 invalid_upstream_response` — the only I11-consistent option, since flushing unpinned or pinning on bookkeeping alone are both ruled out. Direct routing arms no hook and is unaffected.

32. **Settlement follows the client-visible terminal.** `settlement_stream` classified only a parsed failure terminal as an error; a source that closed the body cleanly after content but before any terminal left `terminal_kind` `None`, which read as a success and settled a limited key at the estimate while the SDK client had received the wrapper's synthesized `response.failed upstream_stream_truncated` (I8 and billing attribution; design §6.4 says mid-stream drop ⇒ error/release). Classifying every `None` as an error would in turn have broken decision 24 (an oversized `response.completed` the parser cannot read but the wrapper relays intact). The settlement layer therefore keeps the last relayed event frame (one reference assignment per chunk; comments, `[DONE]` and the Codex keepalive excluded) and, when the parser saw no terminal, reads that frame's kind: a relayed success terminal stays a success, anything else is `error model_source_stream_truncated` and releases. Native Codex streams already raised `ProxyResponseError` on the same shape and are unchanged.

33. **Header and first-frame deadlines are Responses-only** (supersedes the deadline half of decision 23). Design v3 §2 lists chat completions as a v1 non-goal and §8.2 justifies the 20 s / 30 s bounds only by `response.created` arriving within milliseconds of the headers. Chat streams have no bookkeeping frame — the first byte is the first token, and llama.cpp / vLLM / Ollama produce it (Ollama its headers too) only after prompt processing — so the shared open cut long Codex prompts on local sources at 30 s with `504 model_source_timeout` where `main` streamed them. `_open_source_stream` takes both deadlines as parameters; `stream_chat_completion` passes `None` for both (the pre-first-token phases fall back to the source's total budget, a `TimeoutError` there keeps the pre-hardening `502 model_source_unreachable`), while the connect bound, the dedicated connector and the mid-stream idle cap still apply to every source stream.

34. **The parity scenario states what is proven.** The account-routing delta asserted probe/foreground parity for *any* pool and strategy, but the only passing property varied `apply_secondary_budget_threshold` identically on both sides while production uses `True` (opportunistic admission) against `False` (foreground); the production-knob instance is the strict xfail of decision 28. The scenario is split into the three statements the tests establish: parity under the production knobs for every strategy outside the drain family (new property, 400 examples), parity under the drain family over a shared budget subset (existing property), and the mixed exempt/exhausted drain pool as the divergence that excludes the drain family from the trigger (the probe's decline, decision 28; I5).

## Decisions (WP-C1 review fixes, round 2)

35. **A client that leaves after a relayed failure terminal is never charged.** `settlement_stream`'s cancel handler keyed only on `first_output_item_seen`: Codex tears the stream down on `response.failed` / `error` while many sources still send `[DONE]` or keepalives before their own EOF, so the generator was cancelled before the completed-normally branch could classify the terminal and a limited key was settled at the cancel estimate. The cancel handler now reclassifies to `error model_source_response_failed` and releases when the holder recorded a failure terminal or the last relayed event frame is one, matching the completed-normally branch (design §6.4; api-keys "Failure terminal is never charged").
36. **The stream usage parser joins multi-line `data:` fields through the shared `extract_sse_data`.** `_capture_frame` json-parsed each `data:` line independently while the public wrapper reconstructs the joined field per the SSE specification, so a source splitting one JSON across several `data:` lines had its event delivered while the parser observed nothing (no content, item, terminal, delta or usage). Parser and wrapper now agree inside one pipeline.
37. **Only TCP establishment is bounded, never the pooled-connection wait.** aiohttp's `connect` timeout also bounds the wait for a free pooled connection, so the 51st concurrent stream to one source (the dedicated pool is 50 per host / 100 total) failed fast as `502 model_source_unreachable` where `main` queued for a slot; `_source_client_timeout` arms `sock_connect` only and the slot wait falls back to the source's total budget (and the 20 s header deadline for Responses streams). outbound-http-clients delta states the pool-wait boundary.
38. **Metric-increment clauses are asserted behaviourally.** `_inc` and the bulkhead swallow a wrong label set, so the four spec clauses that end in a counter increment (`…dispatch_total{kind,status}`, `…dispatch_abandoned_total{stage}`, `…bulkhead_rejections_total{source_id}`, `…usage_estimated_total{cause}`) are asserted with a recording counter fake in the module that owns the increment.

## Decisions (WP-C1 review fixes, round 4)

39. **The stream usage parser ignores one leading UTF-8 BOM, like the reassembler.** `_iter_source_sse_event_blocks` strips a leading BOM and delivers the frame; the parser did not, read the field `\ufeffdata` on the stream's first record and observed nothing, so a BOM-prefixed data-only `response.completed` reached the client with the pre-content hook bypassed (I11) and its usage never captured (a limited key settled at the estimate). `feed()` drops one BOM from the first non-empty decode; a BOM inside the stream stays unparsed on both sides, so parity holds there too (outbound-http-clients delta sentence + scenario).
40. **Settlement follows the client-visible terminal in the completion branch as well** (extends decision 32). The parser's `completed` / `incomplete` was taken as a success even when `_normalize_public_stream_payload` rewrote the terminal into `response.failed` (`response` not an object → `invalid_json`, invalid output items → `invalid_output_item`): row `success`, limited key settled at the estimate, wire carrying a failure. The completed-normally branch now reads `relayed_terminal_kind(last_event_frame)` exactly as the cancel branch does; a parsed success terminal whose relayed frame is a failure is `error model_source_response_invalid` — a new stage-naming code, because the source did not fail, its terminal violated the public contract — and releases. Clean EOF (`model_source_stream_truncated`) and a relayed success are unchanged (api-keys delta sentence + scenario).
41. **The cancel estimate keys on delivered content, not on the parser's output item** (revises decision 15's wording). `first_output_item_seen` is a parser observation: a `*.delta`-only or completed-only answer delivered to the client and then cancelled was released (under-billing), while an output item observed on a chunk still withheld ahead of an in-flight pin write was charged although zero bytes reached the client (over-billing). `SourceUsageHolder.content_delivered` is set by `_source_stream_body` exactly where a content-carrying chunk is handed to the consumer (live path; after the hook on the withheld and EOF-tail flushes; never on a failure-terminal flush), the owner mirrors it, and `settle_or_release` charges the cancel estimate only when it is set. The cancel handler also gains the success counterpart of decision 35: a client that leaves right after the relayed `response.completed` / `response.incomplete` received the whole answer and is recorded `success`, settled like a completed stream (api-keys requirement reworded, four scenarios).
42. **The drain-strategy divergence is excluded from the trigger** — see decision 28 (rewritten): the probe takes the caller's settings snapshot and declines for `sequential_drain` / `reset_drain` / `single_account` with `codex_lb_pool_exhaustion_probe_declined_total{reason="drain_strategy"}` and an INFO reason line; the strict xfail became a positive decline test plus a premise test. Drain strategies never trigger overflow in v1.

## Decisions (WP-C1 review fixes, round 5)

43. **Delivery is decided at the settlement layer, not at the body's flush point** (extends decision 41). `_source_stream_body`'s flush point sits below the public wrapper, so its flag meant "handed to the wrapper chain", not "on the wire": under the SDK contract `_normalize_public_stream_payload` drops every event outside `response.*` / `error` (a vendor `codex.rate_limits` frame the parser classifies as content, unknown type ⇒ content), `response.*` frames arriving before `response.created` are parked in the pre-created buffer (and discarded on replay when they carry indexed lifecycle), reasoning-summary deltas are held for cleaning, and a `response.created` + content pair coalesced in one source chunk is split into two `send()`s. In each case the body flag was set while the client had received no content, and a limited key that left was charged the cancel estimate — the zero-bytes over-billing decision 41 was meant to close. `settlement_stream` now sets `SourceDispatch.content_delivered` when it hands the transport an event frame `relayed_frame_delivers_content` classifies as content (the parser's own `classify_responses_frame`: content or success terminal; comments, `[DONE]`, the Codex keepalive, bookkeeping, failure terminals and frames without a typed event are not), `observe_stream()` no longer mirrors the holder's flag, and `settle_or_release` keys on the owner's flag alone. `SourceUsageHolder.content_delivered` stays as the body's hook-ordering evidence (I11: the hook completed before any content byte left the body) and is not consulted for billing. The residual ambiguity is the single `send()` in flight when the client leaves; it is resolved as delivered because the frame left the proxy. The predicate is evaluated only until the first content frame (a string slice on the wrapper's `event:` line; a JSON parse only for raw data-only pass-through), so the per-frame cost is one `startswith`.

## Decisions (WP-C1 review fixes, round 6)

44. **The chat-completions stream open returns at the headers, as on `main`** (completes decision 33). Decision 33 kept the header and first-frame deadlines off chat streams but left the shared open reading the first chunk, so the direct chat route held the `200` and headers back until the first token — up to the source's total budget (600 s) — with no disconnect watch: a client abandoning the request during prompt processing freed nothing (upstream connection, dedicated-pool slot, API-key reservation, source compute) until the first token or the budget. `_open_source_stream` reads the first chunk only when a first-frame deadline is armed for that phase (Responses); without one it returns at the headers exactly as `main` did, and `_source_stream_body` reads the first chunk itself under the total budget alone (same verdicts the open gave that phase: `model_source_unreachable`, `invalid_upstream_response`), stamps `first_frame_at` and arms the idle cap only after it. A client that leaves during prompt processing now cancels the body, and the transport latch releases the connection and the lease at once; the route-level test drives a real ASGI disconnect. The Responses open is unchanged (it has the disconnect watch and both deadlines).
45. **Every source route relays the source `Retry-After`.** `ModelSourceForwardingError.retry_after` was merged into the error headers only by `_source_responses_response`; the chat stream and non-stream handlers, the buffered limited-key chat stream, embeddings and transcription dropped it (spec: preserved "for the caller"). All five use `_source_error_response_headers` now; one route-level test per family.
46. **A CRLF split across chunks is one line ending to the parser.** `SourceStreamUsageParser.feed` normalized CRLF per chunk, so a CR closing one aiohttp chunk and its LF opening the next became `"\n\n"` — a spurious frame boundary that cut a frame into two halves parsing to nothing while the event-block reassembler delivered the whole event (usage lost; with a hook armed, the frame flushed at EOF with the hook bypassed, I11). The parser carries a trailing CR across feeds and drops the LF that completes it; a CR followed by a chunk opening with its own CRLF stays two line endings, matching the reassembler's `swallow_lf`.
47. **A typeless error record is the failure terminal on every side of the pipeline.** The wrapper's `classify_event_type` reads a data record without `type` carrying an `error` object as `error` (relayed verbatim in native mode, rewritten into `response.failed` in SDK mode); the parser and `_relayed_event_type` read only a string `type`, so the same record was `non_content`: withheld as bookkeeping ahead of a pin hook until EOF, `cancelled` + estimate when a native client tore down on it, `model_source_stream_truncated` in SDK mode. Both now read the type through `classify_event_type`, so the record is `error model_source_response_failed` and released everywhere.
48. **The client-visible terminal is latched, not read from the last frame** (completes decisions 32/40). `settlement_stream` kept the last relayed event frame, so a typed event trailing a terminal reset the classification: deltas a source kept emitting after the wrapper rewrote its `response.completed{response: null}` into `response.failed invalid_json` made the attempt a charged `success`; a delta behind a relayed failure before a tear-down made it a `cancelled` at the estimate; a vendor frame after an oversized `response.completed` demoted a delivered answer to truncated. The latch takes each relayed terminal kind as it passes — failure sticky, success until a failure follows, non-terminals ignored — in both branches, at the cost of one `startswith` and a slice per `event:`-framed frame (a JSON parse only for raw data-only pass-through blocks: native-mode terminals, unparseable blocks). The parser-saw-nothing + relayed-failure shape stays `model_source_stream_truncated` (the wrapper's own synthesized truncation is exactly that shape); the billing outcome — release — is identical.

## Decisions (WP-C1 review fixes, round 7)

49. **The settlement layer reads relayed frames with the SSE parser's line rules.** `_relayed_event_type` read the `event:` line LF-only, so a spec-legal bare-CR framed block (`event: response.created\rdata: …\r\r`, relayed verbatim by the wrapper) yielded the whole frame as the type, `classify_responses_frame` called it an unknown content-bearing type, `content_delivered` latched on bookkeeping and a limited key that left after only `created`/`in_progress` was charged the cancel estimate instead of released (route repro on `/v1/responses` and `/backend-api/codex/responses`). Its raw-block fallback also split on `str.splitlines` (Unicode breaks that sit unescaped inside a JSON string) and read only the first `data:` line, so a multi-line `data:` terminal was never latched. Both now go through `app/core/utils/sse.py`: the `event:` value ends at `_SSE_LINE_BOUNDARY` (CR, LF or CRLF) and a raw block's type is `classify_event_type(parse_sse_data_json(frame))` — the same joining the parser and the public wrapper apply — so the settlement layer classifies exactly the frame the client parses.
50. **An empty chat-completions `2xx` stream ends the started body cleanly; the row keeps the verdict.** Decision 44 moved the chat first-chunk read into the body, so a source that answered `2xx` and closed before any chunk raised `502 invalid_upstream_response` *after* the `200` and headers were sent: the exception left the ASGI app (uvicorn "Exception in ASGI application" traceback, aborted chunked body) where `main` relayed a clean empty `200`. `_first_source_chunk` now returns `None` at EOF and `_source_stream_body` ends (transport released, `first_frame_at` never stamped). The two chat consumers read the verdict from their own evidence — no chunk arrived — because hand-built holders in tests never stamp `first_frame_at`: the unlimited settlement wrapper records `error invalid_upstream_response` (reservation released through the usage-less settlement, no exception out of the body), and the limited-key buffered handler, which has sent no byte, raises the open's own `empty_stream_error` into its existing error branch (`502`, reservation released, `upstream_status_code` recorded). The Responses open, which reads the first chunk before any client byte, is unchanged. Spec sentence corrected: it had stated the `502` as the client-visible outcome of the started body.

## Alternatives considered

- Folding the schema into the settings/dashboard stage: rejected — re-parenting a migration behind a long-lived feature branch is what stalled #1664.
- Cascading `source_id` deletes: rejected — pins must keep answering lookups during the drain window.
- Partial unique indexes or a request-log column for pins: rejected by the design (§9.1); `pin_key` namespacing carries the uniqueness.

- Returning the preflight from `PUT /api/settings`: rejected — every settings save would query the registry and the pin table (decision 10).
- Validating the designated source's enabled state: rejected — disabling is a kill switch (decision 9).

## Risks

None at runtime in the schema stage: no code path reads the new columns or table, so the request path cost stays at the one warm `SettingsCache.get()` already performed. Downgrade drops the index, the table, and both columns; the pin table is empty and the settings columns are NULL until later stages write them.

In the settings stage the designation is stored, validated, and displayed but never consulted by routing: an operator who designates a source today sees the dashboard's staged-rollout notice and the preflight, and the pool keeps answering `429 usage_limit_reached` (pinned by an end-to-end test). Dangling ids (source deleted out of band, restored database) mean "off" by definition and are shown as such in the dashboard.
