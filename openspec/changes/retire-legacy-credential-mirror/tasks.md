## 6. Review round — the predicates the compat lock was hiding

Lifting `compat_user_locked` makes a *disabled bootstrap account that still holds a password hash* reachable for the first time. Three predicates counted only active rows and were wrong about it; each is fixed the same way — the install is every account it holds, whatever its status.

- [x] 6.1 `create_first_admin`: widen the re-arm compare-and-set from `password_hash IS NULL` to "not an **active** password holder" (`or_(password_hash IS NULL, status != 'active')`) — the same fact the gate above it tests. A disabled row keeps its hash, so the old predicate never matched it again: the local form refused the account (`disabled_user`), setup answered `409 password_already_configured` forever, and `PATCH/DELETE /api/dashboard-users` and `POST /api/dashboard-users` all answered `409 admin_account_required` because the implicit local principal holds no account — no in-product way back on a proxy install. Restore `status`, the admin preset and `role_source=manual` in the same UPDATE (the row setup hands back is the install's way in), and move the `is_break_glass` check into the statement so the read and the write cannot disagree. The stray-row rule is unchanged: a row that merely carries the name `admin` without the designation is still never re-armed.
- [x] 6.2 `remove_password`: the solo gate becomes "the install holds exactly one account" (`get_user_counts().total == 1 and .active == 1`) instead of `count_active_users() != 1`; delete `count_active_users` from the repository, the protocol and the fake (it had no other caller). Returning a passwordless install while a disabled row survives strands that row for good — the implicit local admin cannot manage users — and the two install-wide TOTP requirements this path clears are only justified by "this account *is* the install". The refusal names deleting the other accounts.
- [x] 6.3 `set_user_totp_secret`: the install-wide `totp_required_on_login` clear moves from "only **active** account" to "only account" (`counts().total <= 1`), for the same reason — a disabled colleague can be enabled again, and `/totp/disable` carries no `security:write`.
- [x] 6.4 `requires_auth` is deliberately left counting active accounts only: a disabled password holder cannot sign in, so making sign-in mandatory for it would produce the door nobody can open that `dashboard_auth_migration_inconsistency` exists to detect. 6.2 closes the route into that state instead.
- [x] 6.5 `app/admin_cli.py`: `reset-password` renders a non-`active` status as the consequence ("cannot sign in until an administrator re-enables it") instead of the bare word. It does not change the status — that is an administrator's decision — and everything else about the command is unchanged.
- [x] 6.6 Regression coverage at the product path: `test_auth_provider_abstraction.py::test_setup_re_arms_the_bootstrap_account_after_it_was_disabled` (proxy install, disabled bootstrap row, setup re-arms and the new password signs in through the local form); `test_dashboard_users_api.py::test_password_removal_is_refused_while_a_disabled_account_exists` and `::test_a_disabled_colleague_still_counts_as_a_second_account_for_totp_disable`; the fake-repository cases in `tests/unit/test_dashboard_auth_password_service.py`; `tests/unit/test_admin_cli.py::test_reset_password_says_so_when_the_account_it_reset_cannot_sign_in`.
