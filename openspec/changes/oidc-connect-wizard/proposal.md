## Why

PR-3a-1 built a native OIDC provider and then, deliberately, rendered nothing. The dashboard today has an `oidc/default` row seeded disabled, a `config` document nobody can write, a test-login endpoint nobody can start, a proof that gates the `enabled` flag nobody can earn, and a `/auth/pending` screen that an OIDC refusal cannot even reach. Every wire fact the interface needs is true and none of it is on screen; the only way to connect an identity provider is a `PATCH` typed by hand.

This change is that interface, and it is three surfaces rather than one. The **connect wizard** is where an operator types an issuer and is refused, inline, by the server's own words — the whole point of PLAN §4.6's pre-flight is that the refusal arrives *before* the provider is on, while the operator still has a session. The **login screen** is where the connection becomes a button, and it is already built: `ProviderBlock` renders "Continue with `<label>`" above the local form and a test already pins the ordering, so this change spends nothing there beyond the failure marker the server redirects to and the tests that pin the label rule. The **pending screen** is where the person the resolver refused is told something useful, and it is the one surface that cannot be built from what exists: the callback `303`s to a bare path with the flow cookie cleared, `pending_identity` is set only on the trusted-header path, and the refused address reaches the audit row and nothing else. Two files of the backend grow a carrier for it here, and nothing else in the OIDC backend is touched.

The failure mode this is written against is published and specific. Immich and Langfuse both shipped an OIDC settings page that let an operator save a configuration and enable it in one motion; both produced installs whose administrators could not sign in and could not get back to the settings page that would have fixed it. The gate that prevents it is not a warning, it is the disabled control: the operator's own browser must complete a round trip through the configuration they just typed before the row may be turned on.

## What Changes

- **A company sign-in card, first in the Organisation group**, gated on the group's own `security:write` and on nothing else, so a session that may not see it learns nothing — no card, no placeholder, no request. Its empty state is an invitation ("Connect company sign-in"), not an assertion that nothing was configured: the API returns the same empty `config` for a row nobody ever wrote and for one whose sealed document will not decrypt, and the interface must not claim to tell them apart. The card renders whether or not a reverse-proxy row exists, which retires the group's "there is no company sign-in method to configure" sentence — it stops being true the moment this card ships.
- **A three-step dialog inside that card**: the connection, the claim names, the test login. Steps (a) and (b) are **one** `PATCH {config}` written when the operator leaves step (b), because the server refuses a partial write and the pre-flight runs against the row as stored. The dialog applies the server's field rules before it sends, since everything the request model rejects comes back as `422 validation_error` with no `param` and cannot be attached to a field. The client secret is required on every write and typed every time; the masked value is evidence, never an input, never re-sent, never stored.
- **The turn-on control is disabled until this card has watched a test login succeed.** Not until `testLoginVerifiedAt` is non-null — that may be another administrator's proof, which the server binds to its own account and refuses with `409` — and not across a reload, which fails closed at the cost of one more test login. The window is opened synchronously in the click handler and pointed at the authorization URL when the start returns; a blocked window falls back to the same tab with an in-flight marker holding an id and two timestamps and nothing else. The server chose the return destination (`/settings?org=1#oidc`) and this change honours it: the organisation deep-link helper takes the query string as well as the hash, and the card's anchor is the id the backend already names.
- **Refusals are rendered where they were earned**: `invalid_provider_config` on the field its `param` names (the server answers in snake case, the form is camel case, so the map is explicit), `oidc_provider_unreachable` where the pre-flight was run, in words naming the issuer and discovery addresses as what to check — it is the start that answers it, so it arrives a step after those fields — `insufficient_delegation` and `config_not_supported` on the dialog, `oidc_test_login_required` on the turn-on control, `oidc_rate_limited` with its wait and **no** automatic retry, because that budget is shared with the public sign-in start and a retry loop locks the operator out of signing in. Five codes join the group's explained set; none of them ever shows the raw server message.
- **The refused sign-ins sheet shows each entry's masked address** beside the address it already shows, so the reference the pending screen hands a refused person matches an entry as text. That is the whole of this change's effect on the rules card. It does **not** make the rules follow the provider: the card is still bound to the reverse-proxy row, so an install whose only company sign-in is OIDC finishes the wizard with a provider that admits nobody and no surface to write a rule on. One card per company sign-in provider is a second concern with its own write path, deferred to a follow-up change rather than promised here.
- **The login screen gains one thing**: a neutral notice for the sign-in failure marker the server redirects to, read by a pure helper over `location.search` so the form still renders without a router. The notice names no cause — the backend collapses every cause into one marker on purpose. Everything else on that surface exists and is pinned by tests here rather than rewritten.
- **The pending screen names the provider and shows a reference.** The reference is the masked form of the address the identity provider asserted (`a***@example.com`, the projection `mask_email` already applies to accounts), computed by the server and carried to the browser in one short-lived sealed cookie the refusal redirect sets and every other destination clears, surfaced through the session response as `login.pending_arrival`. The refused sign-ins sheet renders the same masked form beside the full address it already shows, so the two strings match as text and an administrator can find the refusal by searching the page. Because `pending_identity` becomes true for that browser, `AuthGate`'s existing clause starts matching and the URL-only trusted-header clause is left exactly as it is.
Not in this change: the step-up dialog's `methods: ["oidc"]` branch, which #2411 shipped with the dialog — it settles the interrupted request as not verified and navigates the page, and `oidc-provider-backend` already specifies it, so restating it here would be a second and conflicting copy. Also not here: one rules card per company sign-in provider (deferred, as above), SCIM and the automatic-account-management card (Phase 3b), audit webhooks and the audit-export card (Phase 5a), custom roles (5b), a second simultaneous identity provider, a provider selector for the rules cards on an install that has two, and anything in the OIDC backend beyond the pending carrier named above.

## Capabilities

### Modified Capabilities

- `frontend-architecture`: the company sign-in card and its three-step dialog, the pre-flight that arms the turn-on control, the login screen's company button and failure notice, the pending screen's provider and reference, and the masked address the refused sign-ins sheet now shows beside each entry.
- `admin-auth`: the sealed refusal marker the pending redirect sets and every other destination clears, and the `pending_arrival` block the session response derives from it and from nothing else.
