## Context

Release N shipped the expand half of an expand/contract: `dashboard_users` became the only thing the code reads, and the three `dashboard_settings` credential columns became a write-only copy of the compat `admin` account so that a replica still running the previous release — which reads them as its credential — kept working through the roll. `20260909_020000_reproject_compat_admin_credentials` then copied the legacy values onto the account row once, before the account row became authoritative. Everything the contract half needs is therefore already true: nothing reads the columns, and the row they were copied from is the row that now decides who may sign in.

Two other release-N affordances exist only because of that mirror, and both are keyed on the *name* `admin`:

- `_write_user` applies its legacy closure only when `user.username == COMPAT_ADMIN_USERNAME`, and `try_advance_user_totp_step` checks the username the first UPDATE returns. A rename in release N would therefore have stopped the mirroring silently — no error, no log, just a replica reading a hash that no longer changes. That is the whole reason the bootstrap username was pinned, and the reason the pin can be lifted only once the mirror is gone.
- Where a mirror was impossible, a refusal stood in for it. `dashboard_users/repository.py` never touches `dashboard_settings`, so "disable/delete of the compat user" — which PLAN §4.2 lists as a mirrored event — was never implemented as a mirror at all. It was implemented as `409 compat_user_locked`.

So the three scope items are one mechanism seen from three sides, and separating them produces states nobody wants: a rename without the mirror removal breaks the mirror silently, a lock removal without the mirror removal lets the compat account be deleted while a previous-release replica still depends on its projection, and a mirror removal without the lock removal leaves refusals whose stated reason ("a previous-release replica would refuse that account forever") is no longer true.

## Goals / Non-Goals

**Goals**
- `dashboard_users` has exactly one writer per credential, and the schema stops carrying a second copy of a password hash and an encrypted secret that nothing owns.
- The migrated `admin` is an ordinary account: demotable, disableable, deletable, resettable and renameable under the rules that apply to everyone.
- No behaviour that lived inside a mirror closure but was never about the mirror is lost.
- An operator who upgrades out of order is told by the process doing the upgrade, not by a paragraph they may not have read.
- A one-account install sees no new control, no new field, and no new word.

**Non-Goals**
- Self-service rename (`PATCH /api/dashboard-auth/me`), a username field at bootstrap, or a rename surface on the personal tier.
- Detecting a live previous-release replica. That needs per-instance version state with a heartbeat; it is a separate concern and this change must not imply it has one.
- H8, H9, OIDC, SCIM, API key policies, custom roles.

## Decisions

### The columns are dropped in this release, not queued for the next one

The repo has a standing rule for retiring a column, written down in `openspec/specs/deployment-installation/context.md` under NEXT-RELEASE QUEUE and demonstrated by the archived `retire-prewarm-canary-column-mappings`: unmap in release X, drop in X+1, because the Helm migration Job runs before old replicas drain. Measured against that rule this change is early — release N (current `main`) still maps all three columns on `DashboardSettings` and loads the row as a full entity, so the drop breaks a release-N replica mid-roll and not only a pre-N one.

The alternative was considered and rejected: unmap the three columns now, add them to `_LEGACY_EXTRA_COLUMNS`, and queue the DDL for N+2. It would genuinely keep an ordinary N→N+1 rolling upgrade working, and on the co-existence question alone it wins.

It loses on what happens to the columns in the meantime. The mirror is what kept them from decaying: with it removed they hold a real password hash and a real encrypted TOTP secret that `DELETE /api/dashboard-auth/password` no longer clears, that a password change no longer overwrites, and that a downgrade past release N would read as the live credential — so an operator who removed their dashboard password would still be leaving a working one behind in the row. Shipping a release that knowingly does that, in order to protect a rolling window that release N had already told operators not to rely on (the version-2 cookie rename required drain-old-first for exactly the same window), is the worse trade. PLAN.md's Phase 5 line also pins the drop to this release, and expand/contract that never contracts is how a compatibility layer becomes permanent.

What the decision costs is paid explicitly rather than hidden: the upgrade order is a stated contract, the release note is an instruction, `docs/deployment/kubernetes.md` carries the Helm-specific sequence, and the guard below makes the worst case loud. A reviewer who disagrees with this trade should reject the migration, not the rest of the change — the mirror removal, the lock removal and the rename are independent of when the DDL lands.

### The guard is a warning in `run_upgrade()`, and it refuses nothing

`app/db/session.py` already refuses to start on a schema/build mismatch, but a guard there would be in the wrong place twice over: it would miss the Helm Job entirely (the path that does the damage) and it would run after the columns were gone. `run_upgrade()` is the one function the CLI, the Job, the entrypoint and `run_startup_migrations()` all pass through, and `inspect_migration_state()` reads `alembic_version` with no side effects before any DDL. `ScriptDirectory` is already imported and `walk_revisions()` already used, so "is the drop about to run" is a short helper, not a subsystem.

It asks `ScriptDirectory._upgrade_revs(target, current)` — the planner `command.upgrade` itself calls — rather than resolving the target string. The hand-rolled version (special-case `head`/`heads`, otherwise treat the string as a literal revision id) reads three of the target forms Alembic accepts as unknown ids and silently says nothing about them: a relative specifier (`+1`, `<prefix>+2`) and an unambiguous id *prefix* both resolve fine inside `command.upgrade` a moment later, so `upgrade +1` from the drop's direct parent would drop the columns with no drain warning at all.

The public spelling, `iterate_revisions(target, current)`, was the first attempt and is the reason this says "the planner" rather than "a `ScriptDirectory` call": it raises `RangeNotAncestorError` for a ledger holding several heads when the target is on one branch — a shape `test_migration_merge_overflow_transport.py` walks and `command.upgrade` handles — so it is a *second* resolver that has to be kept in step with the first. Calling the one the command calls makes the check and the command agree by construction. The private name is the cost, and it is pinned by tests for every target form.

**The guard does not refuse an N-1→N+1 jump, and an earlier draft of this design was wrong to.** The drop descends from `20260909_020000_reproject_compat_admin_credentials`, so a single `upgrade head` from any older revision applies the backfill and the reprojection and only then the drop: the credentials are on the account rows before the columns they came from disappear. The two-step remedy that refusal demanded applies exactly the same revisions in the same order, so it would have bought no data safety at all — while `run_startup_migrations()` is the boot path, which means the refusal stopped every install of an earlier release from starting. It also contradicted the standing contract that an old ledger reaches head in one command (`test_postgresql_startup_migration_auto_remap_legacy_head`, and every index-repair migration test that upgrades to an old revision and then to head). The ordering that makes the jump safe is worth asserting, but it is a property of the revision graph, so it is asserted once by a test (`test_the_credential_revisions_are_on_the_single_head_path`) rather than re-derived at every boot.

What is left is the honest part. When the drop is about to run on a non-empty database, one `WARNING` names the drain requirement. "Non-empty" is read off the schema, not off the ledger: an `alembic_version` that is absent, truncated, or restored without its rows looks exactly like a fresh install, and that database is the one that most needs telling — the replay it triggers walks the whole chain (the early revisions are inspector-guarded, so it does not fail first) and drops the columns for real. `dashboard_settings` is the table those columns live in, so its presence is the evidence that there is an install here for an earlier-release replica to be serving; an empty ledger **and** no such table is the only shape that stays silent. `codex_lb_fresh_install` cannot stand in for that: it is false the moment an `alembic_version` table exists, so a first run that died after creating that table and before applying anything would be warned to drain replicas over columns this database has never had — and a published revision already reads that attribute to choose its defaults, so it is not free to redefine. That is the limit of what the process can know: nothing anywhere reports a *running* previous-release replica, so the co-existence window is an instruction to an operator, not a condition any check can verify — and a refusal keyed on the ledger would have been a proxy for a fact the ledger does not hold. No flag, no environment variable, no `Settings` field, no budget movement.

### The published revisions are not edited; the replay is stopped before them

A database whose ledger does not describe it gets the chain replayed over it, and this repo's revisions are written to survive that: `_bootstrap_legacy_history()` exists precisely to place such a database at the revision its own data proves it reached, and `_remap_legacy_alembic_revisions()` repairs a ledger written by an older id scheme. After this change one replay is no longer survivable. `20260213_000600` and `20260213_000700` re-add `password_hash`, `totp_secret_encrypted` and `totp_last_verified_step` to an *existing* `dashboard_settings` as empty columns; `20260909_020000` then reads that emptiness as "the previous release removed the password" and NULLs the credential on the bootstrap account row, which after this release is the only copy. Measured on a real database: seed the account row, drop `alembic_version`, `upgrade head` — the row comes back `(None, None)` and the install cannot sign in. Rewind the ledger further back instead and it does not even get that far: `20260909_010000` fails on `no such column: password_hash`, which is how the existing legacy-id remap tests surfaced this.

The obvious fix is a guard inside those revisions, and it is the wrong one. They are ancestors of `main`. An install that has already applied a revision never applies it again, so a guard added there is dead for exactly the installs it was added to protect; and a shipped revision id whose body changed now names two different histories. So the defence goes where the replay is decided instead: `run_upgrade()`, which sees the database before the first revision does.

It needs a signal that outlives the ledger, so the signal is data. The drop revision writes a `runtime_sentinels` row naming itself and removes it on downgrade — the same insert-if-absent table the encryption-key fingerprint already uses. Only that revision writes it, so the marker means the columns are gone *whatever the ledger says*, and a ledger that disagrees is the thing that is wrong. `run_upgrade()` reads it right after the legacy-id remap (it needs a ledger Alembic can resolve) and does what the other two repairs do: stamp at the revision the data proves was reached, then upgrade forward from there. Stamping at the *drop* revision rather than at an ancestor is the honest statement — the marker is written by that revision, so it is the one revision the database has proved it ran. The warning says out loud what the ledger claimed and what was stamped, because a process that quietly rewrites a ledger should not be quiet.

Two things are deliberately left alone, so this cannot become a general-purpose ledger rewriter: a database with no marker replays exactly as before, and a ledger naming a revision this build cannot resolve is untouched so `command.upgrade` raises the error the repair tests already pin.

### Rename is an admin action on an account, not a field at bootstrap

PLAN §4.2 says the pin's successor is "이름 변경" — a rename, which is the same sentence that carries the release-N `compat_user_locked` refusal of "삭제·이름 변경". PLAN §4.11 tier (a) then describes the personal install as "부트스트랩 → 비번 1개(아이디 없음, 조용히 `admin`)" and lists "아이디 칸" among the things that tier **hides**, with rule ② banning the vocabulary outright from personal copy. A username box on the bootstrap screen would therefore move the personal tier backwards for every self-hoster, and it would do it on the one screen §7's compatibility checklist still describes as "부트스트랩 전 설치는 로컬/토큰 부트스트랩이 첫 admin(`admin` 고정)을 만든다".

A rename lives in the People tab, which the personal tier does not render. So the individual install sees zero change — not a hidden field, not a disabled control, nothing — and the requirement "keep the individual-install experience unchanged when there is one account" is satisfied by construction rather than by care. The consequence, stated plainly because it is a real limitation: a one-account install cannot rename its account at all. That is the correct trade. The name is never displayed on that tier, never typed (the login form hides the field), and never sent; adding a control for it would introduce the concept to the only persona that is supposed to never meet it.

`PATCH /api/dashboard-users/{id}` is the home rather than a new endpoint: it is already the route whose compat refusal this change deletes, it already carries `users:manage`, step-up and `assert_can_act_on`, and its schema already forbids unknown fields, so `username?` is an additive field on an existing contract. Self-rename through `PATCH /api/dashboard-auth/me` is deliberately not added — an admin can do it, the plan does not ask for it, and every surface not added is a surface that cannot leak.

### The `admin` reservation survives the rename, so the rename is one-way

`_new_username()` refuses `admin` for account creation and invite acceptance; `_free_username()` skips it so a proxy identity called `admin` becomes `admin-2`. Keeping both means you can rename the bootstrap account *away* from `admin` and never back, and no one else can take the name.

That asymmetry is deliberate. `docs/sso.md`'s recovery runbook, `docs/authentication.md`'s reverse-proxy section and every operator's muscle memory treat `admin` as "the local emergency account"; letting an ordinary member acquire the name once the break-glass account has moved off it is a confusion hazard during exactly the incident the runbook exists for, and buys nothing anybody asked for. Narrowing the reservation to an ordinary `username_taken` would be cleaner product behaviour and is the obvious follow-up, but only after the re-arm predicate stops keying on the name — which this change does, so the follow-up is cheap whenever someone wants it. Leaving the decision unstated is the one option that is not available: silence here reads as an oversight.

### First-run setup re-arms by row, because the name is no longer stable

This is the trap the rename creates and it must be closed in the same change. `create_first_admin` looks up `WHERE username = 'admin'` and inserts `COMPAT_ADMIN_USER_ID`. Rename to `alice` → `DELETE /api/dashboard-auth/password` (which clears credentials but keeps the row) → `POST /password/setup`: the lookup misses, the insert collides on the deterministic id, `IntegrityError` becomes `None`, and the caller is told `409 password_already_configured`. A renamed install could never be re-bootstrapped, and the symptom names nothing.

The fix is to key the lookup on the same fact the refusal already keys on: `The username admin is reserved` says setup "MUST re-arm an existing credential-less row only when it is the bootstrapped break-glass row (`is_break_glass` with the compat id)". The code simply catches up with the spec. The new account keeps the frozen id, so the id remains a stable handle for the bootstrap account no matter what it is called — which is also what makes the migration's downgrade projection deterministic.

### The replay guard keeps its shape, including the rollback

Deleting the second `UPDATE` is the easy half. The half that matters is the commit boundary: `try_advance_user_totp_step` flushes the user-row advance, and on a refusal calls `session.rollback()` before returning `False`. `disable_totp` depends on that boundary — it consumes the code (which commits) *before* the break-glass guard, because a commit between the guard's count and the secret write would drop the write-intent lock and let two concurrent disables both pass (PLAN F5), and `verify_step_up` shares the same helper. So the surviving statement keeps the rollback-then-`False` shape rather than becoming a bare conditional UPDATE whose failure leaves the session mid-transaction. `tests/integration/test_local_login_policy_break_glass.py` pins the `try_advance_user_totp_step` → `acquire_write_intent` call order and must keep passing untouched.

### Removing the mirror removes a retry loop, but not a compare-and-set

Mirrored writes committed through `SettingsRepository.commit_refresh`, which carries the optimistic `dashboard_settings.version` guard; that is the only reason `_write_user` runs `_apply()` twice and `create_first_admin` loops twice. Those loops go with the mirror. What does **not** go is `create_first_admin`'s compare-and-set (`WHERE password_hash IS NULL`, unique username, the deterministic id), which protects against a second setup rather than against a settings race, and which the `First-run setup is compare-and-set` requirement owns. The paths that still write settings — bootstrap-token invalidation and the requirement resets — keep `commit_refresh` and keep their single retry, because they are still settings writes.

### The install-wide writes stop being conditional on a name

Three of the closures carried behaviour that was never about the mirror, and the closure's `username == 'admin'` gate was an accident of where it was written:

- **Bootstrap-token invalidation** on setup and password change. Unconditional now. The token is inert once any account holds a password, so clearing it on any password write is both defensive and simpler than asking which account wrote.
- **Both TOTP requirements reset on password removal.** Unconditional now, which is safe because `DELETE /api/dashboard-auth/password` is already gated on the personal-install condition (one active account, no other rows, no pending invite, no non-password provider). This is a fix: on a renamed install the name-keyed version would have silently stopped resetting them, leaving `requires_auth` true with nobody able to sign in.
- **`totp_required_on_login` off on self-service TOTP disable.** *Not* made unconditional. `/totp/disable` is a self-service route carrying no `security:write`, and under release N a compat `admin` in a team could use it to turn an install-wide security setting off. The condition becomes the one that actually justified the behaviour — the acting account is the install's only account, counting disabled ones and live invitations rather than only the active rows, because a disabled colleague is an account that can be enabled again and an install-wide requirement must not come off because somebody else's sign-in happens to be switched off today — so the personal install keeps today's "I turned two-factor off" outcome and a team member cannot move an install-wide setting from a self-service route. `preserve_policy` therefore stays a parameter of `set_user_totp_secret`, with administrative `reset-totp` continuing to pass it.

### `compat_user_locked` leaves in one piece, both classes

`CompatUserLockedError` and `CompatAdminUnenrolledError` are different classes in different modules mapped to the same wire code, which is why grepping the class name finds only three of the four refusals. Removing three and leaving the fourth would ship a half state: the People tab's Reset two-factor row action would work while the settings toggle it points at still answered `409`. They go together, and `TotpEnrollmentSummary` loses `compat_admin_unenrolled` in the same diff.

One thing not to "fix" on the way out: the PATCH guard fires only on role/status, so an `isBreakGlass`-only PATCH on the compat row is allowed today even though `local-login-policy-and-break-glass`'s spec text claims the compat lock applies first to that field. The mismatch disappears with the lock. Tightening the guard in its final release would be a behaviour change disguised as a cleanup.

### The login form's anti-flap rule stops keying on the literal `admin`

`login-form.tsx` keeps the username field visible whenever the remembered username is anything other than `admin`, and the `Login form username disclosure` requirement says so normatively. The literal was a proxy for "the default bootstrap name"; once the account can be renamed it is just a name, and an install that renamed itself to `alice` and then shrank back to one account would start showing a username box it does not need — the P5 regression this change is supposed to avoid.

The re-key is to make the rule converge instead of comparing to anything: a remembered username still keeps the field visible (that is the anti-flap intent — the form must not change shape while the install is genuinely multi-account), and the client **forgets** the remembered username after a successful sign-in whose session reports `login.usernameField === "hidden"`. An install that returns to one account therefore shows the field once and is password-only from the next visit, whatever the account is called. The never-renamed install behaves exactly as today; every other name now converges too, which the literal-keyed version never did.

### The dead projection class is called out rather than quietly deleted

`CompatAdminProjection` has no constructor call anywhere in `app/` or `tests/`, yet its docstring describes itself as the funnel every legacy credential write passes through. Deleting it is trivial; *saying* it was already unreachable is not optional, because the natural way to review a change called "retire the legacy credential mirror" is to open the file named after it, conclude the change is one deletion, and miss the seven call sites in `DashboardAuthRepository` and the eighth in `admin_cli.py`. The two constants it exported are the only live thing in it, and `tests/unit/test_dashboard_users_compat.py` — which asserts the two migrations' frozen literals still equal the runtime constants and that the revisions import nothing from `app.*` — is the reason they must land somewhere rather than disappear.

## Risks / Trade-offs

- **The upgrade window is the real cost of this change.** Mitigated by the stated contract, the docs, the ledger guard and the unconditional warning; not eliminated. Accepted deliberately (see the first decision).
- **`tests/integration/test_affinity_identity_migration.py` breaks in two places and neither failure names the cause**: `_seed_history()` UPDATEs all three dropped columns at head, and `_projected_rows()` indexes a `dashboard_settings` snapshot column-by-column after upgrading past the drop, raising `KeyError`. The suite is about unrelated merge history, so the breakage reads as an unrelated regression. Its seeding must move to `dashboard_users` and its snapshot must tolerate the drop.
- **Removing `compat_user_locked` from `reset-totp` removes the last guard that kept `totp_required_on_login` and a secretless compat admin from coexisting.** That is the intended unblock, and the resulting state (an account held at `totp_enrollment_required` until it enrols) is the ordinary one every other account already lives in.
- **`set_user_password_hash` becomes fully dead** once the mirror goes: no production caller, only the protocol stub, the unit-test fake and the mirror-conflict test. Deleting it touches three files and will look like unrelated churn unless it is read as part of this list.
- **i18n parity**: `access.errors.compat_user_locked` exists in `en`, `ko` and `zh-CN` and the parity test compares full key sets, so it leaves all three or none. The three MSW handlers that manufacture the code go with it, or the frontend tests keep passing against a fiction.
- **The unit-test fake in `tests/unit/test_dashboard_auth_password_service.py` re-implements the mirror contract**, including a `totp_required_on_login = False` that ignores `preserve_policy`. If it is not updated to match what survives, it will hide the behaviour change in `set_user_totp_secret` rather than catch it.
- **Copying the wrong canonical block** is the quiet failure mode of this change: `dashboard-users` has no folder under `openspec/specs/`, `openspec validate` never resolves a MODIFIED header against a base, and three of the requirements edited here exist in two versions (`Editing an account` — take `role-mappings-and-organization-group`; `First-run setup is compare-and-set` — take `auth-provider-abstraction`; `People tab` — take `enable-operator-viewer-presets`). Each MODIFIED block in this change was diffed by hand against its newest source.

## Migration Plan

1. Land the code so nothing writes the three columns and nothing named `admin` gates behaviour except the two name reservations.
2. The Alembic revision, parented on the current single head `20260912_000000_merge_thread_cache_and_bridge_retirement_heads` (re-pointed from `20260911_030000_add_local_login_policy` when `main` advanced under this branch), drops the three columns with `op.batch_alter_table` behind `sa.inspect(bind).get_columns()` checks in both directions so the body is idempotent on re-run. The downgrade re-adds them nullable and re-projects from the `dashboard_users` row carrying the frozen compat id, which is the mirror image of `20260909_020000` and is the only deterministic source once the account can be renamed; the revision freezes that literal rather than importing it.
3. Ship the guard in `run_upgrade()` in the same PR as the revision, so no build exists in which the DDL runs unguarded.
4. Release note, `docs/deployment/kubernetes.md` upgrade sequence, and the rollback-to-release-N-only limit.

## Open Questions

- Whether to narrow the `admin` reservation from `422 validation_error` to an ordinary `409 username_taken` in a later release, making the rename two-way. Deliberately deferred; this change makes it cheap by removing the name from the re-arm predicate.
- Whether a per-instance version sentinel with a TTL heartbeat (so an upgrade can actually detect a live old replica instead of inferring it from the ledger) is worth a table. Out of scope here, and the release note does not pretend otherwise.
