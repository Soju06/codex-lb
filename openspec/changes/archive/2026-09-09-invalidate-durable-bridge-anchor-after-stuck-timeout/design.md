## Context

The HTTP Responses bridge persists a durable session row per `bridge_key` (`http_bridge_sessions`) so a reattach after a local process restart or idle retirement can resume the same logical conversation. When a fresh reattach has no client-supplied `previous_response_id` and the durable row has a `latest_response_id` on file, `streaming.py`'s `fresh_reattach_can_use_durable_anchor` injects that response id as the anchor (`fresh_reattach_anchor_injected`) and marks the request `proxy_injected_previous_response_id = True`.

`recover-codex-desktop-idle-bridge` added a 240-second client-safe deadline (`_HTTP_BRIDGE_EVENTLESS_RESPONSE_CREATED_MAX_SECONDS`) for a `response.create` that never produces `response.created` or any other response event, and fails the request closed as `missing_response_created_timeout` without transparent replay or account penalty. That is deliberate: the request cannot prove replay safety, so it must not silently retry.

The unaddressed half is durability: `_close_http_bridge_session` releases the durable lease (`release_live_session`) but never touches `latest_response_id`, `latest_input_item_count`, `latest_input_full_fingerprint`, or `latest_pending_tool_calls_json`. The next reattach on the same `bridge_key` resolves the same durable row, finds the same `latest_response_id`, and injects the identical anchor into an identical `response.create`, which stalls the same way. Only a client that discards its own local continuation and starts a fresh session (no `previous_response_id`, no matching turn-state/session-header alias) escapes the loop.

[#1534](https://github.com/Soju06/codex-lb/issues/1534) is a clean production reproduction of exactly this: no `custom_tool_call` items, no interleaved `developer` messages (so the `preserve-fresh-bridge-full-resends` / [#1537](https://github.com/Soju06/codex-lb/pull/1537) prefix-scanner producer does not apply), a plain idle-retire-then-reattach sequence that repeats `fresh_reattach_anchor_injected` -> `missing_response_created_timeout` every subsequent turn. The reporter's own log excerpt shows the client resending its complete stored history (~425 items) on that reattach — i.e. this specific reproduction is a full-resend client.

`streaming.py` supports two materially different shapes behind the same `proxy_injected_previous_response_id = True` flag, and the difference matters once the anchor is gone:

1. **Full-resend clients.** The incoming payload already contains the whole conversation (`_http_bridge_payload_looks_like_full_resend`); the anchor is a bandwidth/cost optimization (trim the already-known prefix). Once the anchor is cleared, the next reattach's identical full payload falls through unmodified and untrimmed — still a complete, correct conversation, just less efficient. This is the confirmed #1534 shape.
2. **Genuine delta-only clients.** `fresh_reattach_can_use_durable_anchor`'s `(not payload_looks_like_full_resend or durable_anchor_trimmable)` clause deliberately also injects the anchor for a payload that is *not* a full resend — the client relies entirely on codex-lb's session/turn-state affinity plus the anchor to carry prior context; there is no local full history in the request at all. The code's own inline comment at the injection site (`streaming.py`, near `fresh_upstream_request_is_retry_safe = False`) states this directly: replaying such a payload without the anchor "would silently turn it into a fresh turn and drop conversational context." For this shape, once the anchor is cleared, the next reattach sends the client's bare follow-up as if it were turn one. If that follow-up is itself multi-part (for example a dangling tool output), upstream is likely to return a 400 error, which is visible to the client. If it is a plain new user message, upstream will accept it as a valid, complete, new conversation: a 200 response with a reply that has no memory of anything before it. That is a silent context-loss failure. Today's 240s stall is visible and bounded; this would not produce any error at all.

## Load-bearing assumption

This change assumes it is acceptable to leave shape 2 (genuine delta-only proxy-injected anchors) on today's repeated-timeout behavior rather than extend the anchor-clear to them, because there is no proof-based way to make clearing safe for that shape without the client itself resending full context. This mirrors the check `preserve-fresh-bridge-full-resends` already applies (never drop an anchor without a positive, checked proof) rather than the more permissive reading of "the retry takes the fresh no-anchor path" from the issue thread, which — read literally and applied to shape 2 — would replace a visible failure with a silent one. The maintainer's own confirmed reproduction (#1534) is shape 1, so this narrower scope still fixes the reported case. Whether shape 2 should get its own fix, and what that fix should look like, is left to maintainer input rather than decided here.

## Goals / Non-Goals

**Goals:**
- Stop a proxy-injected durable anchor that has already proven eventless from being re-injected into a later, distinct request on the same durable session — but only when doing so cannot silently drop conversation context.
- Keep the fix narrowly scoped to the state that caused the stall: only the response-id anchor and the state bound to it, not the durable session's identity, turn-state, or aliases.
- Preserve the durable-write fencing invariant used everywhere else in this repository/coordinator: a write only lands while the caller still holds the current `owner_instance_id`/`owner_epoch`; a fenced-out caller's write is a safe no-op.

**Non-Goals:**
- No change to the eventless deadline's value, its terminal failure code, or its no-replay/no-penalty behavior for the timed-out request itself.
- No change to client-supplied anchor handling. A client that supplies its own `previous_response_id` owns that decision; this change never clears an anchor codex-lb did not inject.
- No change to cross-account recovery, owner-unavailable handling, or the account-neutral replay rules — those already have their own turn-state-clearing path (`Cross-account bridge retries clear turn-state`).
- No overlap with [#1394](https://github.com/Soju06/codex-lb/pull/1394)'s in-flight recovery mechanisms (`recover-fresh-hard-bridge-timeouts`, `recover-safe-http-bridge-continuations`), which operate on the *same* request before it settles and explicitly keep proxy-injected-anchor requests without a proof-gated full-resend body pinned and fail-closed. This change operates on the durable row *after* settlement, for the *next* distinct request.
- **Does not extend to genuine delta-only proxy-injected anchors** (shape 2 above). See Load-bearing assumption.

## Decisions

- **Clear only the four anchor-bound columns, fenced by owner epoch.** Add a repository method modeled on the existing `renew_session`/`release_session` fenced-update shape: `UPDATE ... WHERE id = :session_id AND owner_instance_id = :instance_id AND owner_epoch = :owner_epoch SET latest_response_id = NULL, latest_input_item_count = NULL, latest_input_full_fingerprint = NULL, latest_pending_tool_calls_json = NULL`. This mirrors what `renew_session` already does whenever `latest_response_id` changes (it nulls the input fingerprint/count together), and what the account-invalidation path (`accounts/repository.py:_close_http_bridge_sessions_for_account`) does for the same four columns, minus the parts of that path (full session closure, alias deletion) that don't apply here.
- **Gate on `proxy_injected_previous_response_id` AND a new `proxy_injected_anchor_had_full_resend_payload` flag, not on the failure code or the injection flag alone.** `missing_response_created_timeout` can also fire for a client-supplied anchor or a turn-state-only reattach with no anchor at all; clearing the durable anchor in those cases would either overreach into client-owned state or be a no-op that adds noise. `proxy_injected_previous_response_id` alone is not enough either — it is true for both shapes above. The new flag captures `_http_bridge_payload_looks_like_full_resend` at the exact moment(s) the anchor is injected (the durable fresh-reattach branch, the owner-forward interrupted-tool-call recovery branch, and the session-level anchor-injection branch, propagated through the later trim re-prepare step), so the eventual clear decision reflects what the client actually sent, not an inference from post-trim state.
- **Do not reuse the existing `fresh_upstream_request_is_retry_safe` field for this gate.** That field already exists for exactly the phrase "is it safe to drop this anchor," which looked like a perfect fit — but tracing it end to end shows it answers a different, stricter question: whether an in-place, same-request replay is provably equivalent to the client's own retry (requires `durable_full_resend_has_safe_fresh_context`: retained assistant-output boundary or exact pending-tool-call settlement). By construction, whenever injection actually happens with a full resend, that stricter proof has already failed (a passing proof takes the earlier `fresh_reattach_full_resend_preserved` branch instead, which never injects at all) — so `fresh_upstream_request_is_retry_safe` is always `False` at the point this new gate needs to fire, including for the confirmed #1534 reproduction. Reusing it would make this fix a no-op for the reported bug. The new field intentionally asks the weaker question this use case needs: not "is this exact payload provably duplicate-safe for an immediate retry," but "does the client demonstrably have the ability to send complete context at all."
- **Clear before releasing durable ownership, not after.** `_close_http_bridge_session` calls `release_live_session`, which sets `owner_instance_id = NULL`. If the anchor-clear ran after that, the fenced update would no longer match (the instance no longer owns the row) and would silently no-op on the common path, defeating the fix. The clear must run while the retiring session still legitimately owns the durable row — inside the `missing_response_created_timeout` branch of `_relay_http_bridge_upstream_messages`, before `_fail_http_bridge_reader_and_maybe_retire` (and therefore before `_close_http_bridge_session`) is invoked.
- **Leave `latest_turn_state` and aliases intact.** The turn-state-based reattach path is a separate, unaffected continuity mechanism; clearing it would force an unrelated full resend even when only the response-id anchor was ever the problem.

## Rejected Alternatives

- **Close/delete the whole durable session on this timeout.** Simpler, but throws away the turn-state-based reattach path along with the anchor, and duplicates the much larger blast radius that `accounts/repository.py`'s account-invalidation path already owns for a different trigger (account status change, not a single stuck request).
- **Clear the anchor unconditionally on every `missing_response_created_timeout`, regardless of `proxy_injected_previous_response_id`.** Would also strip a client-supplied anchor the client still intends to use, which is out of scope and not this proxy's call to make.
- **Clear the anchor whenever `proxy_injected_previous_response_id` is true, without the full-resend check.** The initial draft of this change did exactly this. Reviewing it against the codebase's own established bar for dropping an anchor (`preserve-fresh-bridge-full-resends`'s proof-gated approach) surfaced that it would silently corrupt genuine delta-only conversations rather than merely fail them faster. Rejected in favor of the narrower, full-resend-gated version.
- **Reuse `fresh_upstream_request_is_retry_safe` as the gate.** Would make the fix a no-op for the confirmed reproduction; see Decisions.
- **Let the in-flight request itself retry without the anchor (transparent replay) instead of fixing the durable row.** Rejected for the same reason `recover-codex-desktop-idle-bridge` fails this request closed in the first place: an eventless `response.create` cannot prove replay safety, so the *current* request must not be silently retried. Only the *next*, distinct request — which the client itself constructs — should see the fresh no-anchor path.

## Risks / Trade-offs

- A full-resend session that idle-retires and reattaches with a proxy-injected anchor loses that anchor's optimization (skipping prefix trimming/resend) after one stuck timeout, even if the stall was transient. This is acceptable because the alternative today is an unbounded repeat of the identical stall on every subsequent turn.
- Genuine delta-only proxy-injected anchors remain unfixed by this change and continue to repeat the 240s stall indefinitely until the client abandons its local continuation state. This is a known, explicit scope limitation (see Load-bearing assumption), not an oversight.
- The fenced write can race a concurrent replica that has already reclaimed the durable row (e.g., the client reconnected to another instance during the 240-second wait). The fence makes this a safe no-op — the newer owner's state is authoritative and untouched — but it means the clear is best-effort, not guaranteed, in that narrow race window.
- File overlap with the open [#1394](https://github.com/Soju06/codex-lb/pull/1394) PR in `durable_bridge_repository.py`, `durable_bridge_coordinator.py`, and `http_bridge/upstream_events.py` may require a rebase after that PR lands; the two changes are functionally independent (see Non-Goals).
