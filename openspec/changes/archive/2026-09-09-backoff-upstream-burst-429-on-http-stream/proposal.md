# Back Off Upstream Burst 429s on the HTTP Stream Transport

## Why

Codex CLI users on production (`codex-lb` 1.25.0-beta.5, 2026-09-09) see `exceeded retry limit, last status: 429`. The load balancer answers those turns with HTTP 429, `code="upstream_error"`, `message="Rate limit exceeded"`: a pass-through of an upstream (ChatGPT backend) **per-account burst/concurrency** rejection whose JSON body carries only a message and no `code` / `type`. It is not a quota event. In 92% of these rejections the same account serves a request successfully within ±3 s; per-account in-flight at rejection time is p50 5 against a baseline of 2. Only the HTTP stream transport is affected (policy `native_codex_http`, `POST /backend-api/codex/responses`, `propagate_http_errors=True`). Current Codex CLI (>= v0.65) makes exactly one attempt per turn on a 429 (`retry_429=false`) and ignores `Retry-After`, so the proxy has to absorb the burst inside the request or the user sees the error.

Two proxy defects turn a few-second burst into a user-visible failure:

1. **The account stays fully selectable.** `_normalize_error_code` maps the code-less body to `upstream_error`, `classify_upstream_failure` yields `retryable_transient`, and `_handle_stream_error` records only the generic transient error (`record_error`); `record_upstream_overload` fires only for the overload codes and `mark_rate_limit` only for coded 429s. Nothing reads the `Retry-After` that `app/core/clients/proxy.py` already parses onto `ProxyResponseError.retry_after_seconds`. Sticky `prompt_cache` routing therefore sends the client's own retries straight back to the account that just rejected.
2. **Failover is a lie for owner-bound requests.** The pre-visible failover block in `streaming/retry.py` logs `Failover decision ... action=failover_next`, excludes the account and re-selects, but Codex multi-turn payloads carry `reasoning` items that are not account-neutral, so `_authorize_payload_dispatch` bound the replay to the failed account (`payload_replay_required_account_id`). The next attempt therefore prefers the failed account with `fallback_on_preferred_account_unavailable=False`, `_select_account_with_budget` logs `Proxy preferred account skipped` and returns `preferred_account_unavailable`, and `retry.py` re-raises the saved upstream 429 immediately (p50 180 ms after the rejection). In 24 h of production traffic 216 of 314 second selections vanished this way. The post-401-refresh copy of the block behaves identically.

## What Changes

- **Fix A — replica-local burst cooldown for unbound selection.** A code-less upstream HTTP 429 recorded through the `_handle_stream_error` funnel (keyed on the HTTP status, so `server_error` rewrites and `detail`-parsed bodies are covered) stamps `RuntimeState.burst_backoff_until = now + clamp(Retry-After, 5 s, 30 s)` (5 s when the header is absent; a rejection while cooling extends, never shortens). `overload_backoff_active` treats the burst deadline like the overload soft backoff, so `unbound_selection.py` / `sticky_selection.py` steer fresh (unbound) selection and fresh sticky bindings away from the account with no edits and with the existing filter contract: the account is dropped only while another candidate remains, and the strategy falls back to the full pool exactly as before. `overload_isolation_active` is untouched, so established soft sticky owners and hard continuity owners are never rerouted by a burst. The existing transient error penalty stays. A `WARNING` `Account burst backoff engaged` names the account (under the redaction policy), the applied seconds and the upstream `Retry-After`. Coded 429s (`rate_limit_exceeded`, `usage_limit_reached`) keep `mark_rate_limit`. `_handle_stream_error` gains a keyword-only `retry_after_seconds` argument; a pure `is_upstream_burst_rejection(failure_class, http_status)` helper is added.
- **Fix B — owner-bound burst 429 retries the same owner with a bounded backoff.** `failover_decision` gains `owner_bound` and `same_account_retry_available` inputs and a third action, `retry_same_account`: an owner-bound request can never cross accounts, so it returns `retry_same_account` while a retry is available and `surface` otherwise, never `failover_next`. The pre-visible and post-refresh failover blocks in `streaming/retry.py` compute owner-boundness from the loop's existing continuity inputs (payload replay binding, required preferred account, file-pin owner, turn-state owner), count same-account burst retries per account (reset when a different account is selected), and on `retry_same_account` keep the account selectable, release the tracked stream lease, write account health (so fix A's cooldown engages for other requests), and wait `min(10 s, max(Retry-After, 1 s * 2^(n-1)))` (1 s, 2 s, 4 s) through the existing header-holding startup wait (`_iter_account_capacity_recovery_wait`, stage `burst_backoff`) so `api.py::_wait_for_first_stream_probe` keeps holding the HTTP headers instead of committing a 200/SSE response, then re-enters the same-account loop. After three retries, or when the request budget is spent, the **original** upstream 429 status and body are surfaced. `retry_after_seconds` is threaded through `_handle_or_defer_keyed_stream_health` and the deferred post-refresh penalty tuple.
- **Honest `Failover decision` log.** The log line keeps its `key=value` shape and reports the action that is actually executed (`retry_same_account`, `surface`, or `failover_next`); a request that is not owner-bound keeps `failover_next`, and fix A then steers the next selection away.
- **`Retry-After` on the surfaced 429.** When the original upstream 429 is surfaced after retries are exhausted, the propagated `ProxyResponseError` carries `Retry-After` (the upstream value when present, otherwise `5`, matching `LOCAL_OVERLOAD_RETRY_AFTER_SECONDS`) so `api.py::_stream_startup_error_response` emits the header.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `account-routing`: a code-less upstream HTTP 429 enters a short replica-local burst cooldown that steers fresh (unbound) selection like the overload soft backoff, without touching rate-limit state, persisted status, or isolation.
- `sticky-session-operations`: an owner-bound request that receives an upstream burst rejection retries the same owner after a bounded backoff while HTTP headers are held, then surfaces the original 429 with `Retry-After`; the failover decision log states the executed action.

No existing requirement in `proxy-runtime-observability` or `responses-api-compat` governs the `Failover decision` log line (grep of `openspec/specs` for `Failover decision` returns nothing), so those capabilities are not modified; the honest-log rule lives in the `sticky-session-operations` delta.

## Impact

- `app/modules/proxy/_load_balancer/types.py` (`RuntimeState.burst_backoff_until`), `app/modules/proxy/_load_balancer/overload_backoff.py` (`BURST_BACKOFF_DEFAULT_SECONDS`, `BURST_BACKOFF_MAX_SECONDS`, `overload_backoff_active` reads both deadlines, `record_burst_rejection_locked`, `record_upstream_burst_rejection`, module docstring), `app/modules/proxy/_service/streaming/helpers.py` (`_handle_stream_error` keyword-only `retry_after_seconds`, HTTP-429 hook), `app/modules/proxy/_service/support.py` (protocol stub), `app/modules/proxy/helpers.py` (`is_upstream_burst_rejection`), `app/core/balancer/logic.py` (`FailoverAction` `retry_same_account`, `failover_decision` inputs, burst same-account constants and `burst_same_account_backoff_seconds`), `app/modules/proxy/_service/streaming/retry.py` (both failover blocks, `_handle_or_defer_keyed_stream_health`, deferred penalty tuple, `Retry-After` on the surfaced error), optionally `app/modules/proxy/service.py` (pass `exc.retry_after_seconds` at the two `_handle_stream_error` call sites only if it fits the line ceiling).
- **No new settings**: all bounds are module constants; the `Settings.model_fields` ratchet stays at 130. **Ratchets unchanged**: `service.py` stays within 2600 lines (2577), `load_balancer.py` (3004/3021), `unbound_selection.py`, `sticky_selection.py` and `streaming/mixin.py` (1098/1100) are not edited. `retry.py` and `streaming/helpers.py` keep zero raw `asyncio.sleep` / `time.*` calls (scheduler and clock seams). No schema, migration, API, dashboard, or error-taxonomy change; all new state is replica-local runtime state that is never persisted.
- Zero-config behavior change: a code-less 429 benches the account for 5-30 s on the observing replica for fresh selections, and an owner-bound request spends up to 1 s + 2 s + 4 s (bounded by the request budget and by upstream `Retry-After`, capped at 10 s per wait) retrying its owner before surfacing. `classify_upstream_failure` outputs, `_ACCOUNT_NEUTRAL_INPUT_ITEM_TYPES`, `mark_rate_limit`, `RuntimeState.cooldown_until` and persisted `RATE_LIMITED` are unchanged.

## Known Limitations

- The burst cooldown is replica-local, like every other transient balancer health signal; peers learn it from their own observations.
- Only the HTTP stream transport is covered. The direct WebSocket and HTTP-bridge transports relabel an upstream handshake 429 to a 502 before it reaches this classification and are left for a follow-up.
- Same-account retries happen only before any downstream-visible output; a burst rejection after output has been emitted is surfaced as today.
- The same-account backoff waits count against the request's startup budget, so a request that arrives with little budget left surfaces after fewer retries.
- Codex CLI ignores `Retry-After`; the header on the surfaced 429 serves other clients and observability, not the CLI's retry loop.
